## 1. プロジェクト概要

### 1.1 プロジェクト名

**ITエンジニア向けタレントマネジメントシステム（TechTalentManagement）**

### 1.2 目的（Why）

金融系グループ会社の社内SEとして、インターネットバンキング等の開発を担うITエンジニアを対象に、評価の納得感向上とモチベーションアップを実現するタレントマネジメントシステムを構築する。

具体的には、リクルート社が実践する **Will-Can-Must** フレームワークと **人材開発委員会** などの会議体運営をベースに、考課フローとタレントマネジメントを一体化させる。エンジニアが自身の成長を実感でき、組織が重点管理人物を適切に特定・支援できる仕組みを提供する。

### 1.3 スコープ（What）

**対象とすること:**
- エンジニアのスキル・技術レベルの記録と管理
- 目標設定・達成履歴管理（OKR / MBO）
- プロジェクト・アサインメント履歴管理
- エンジニア評価・考課ワークフロー（申請・承認・フィードバック）
- 会議体管理（人材開発委員会などの運営支援）
- 個人の中長期キャリアプランの管理（v1は本システム内で完結。外部連携はv2以降の検討事項）

**対象としないこと:**
- 給与・報酬計算処理（既存の給与システムと連携するが、本システムでは行わない）
- 採用管理（採用フェーズは対象外）
- 勤怠管理（既存システムと連携するが、本システムでは行わない）

### 1.4 成功の定義

- [ ] エンジニアが自分のスキル・目標・評価履歴を一元的に参照できる
- [ ] 考課ワークフローが完全にデジタル化され、紙・Excelが不要になる
- [ ] 重点管理人物の設定と育成計画が組織として管理できる
- [ ] 人材開発委員会など会議体の準備・記録コストが50%以上削減される
- [ ] エンジニアの評価納得度（サーベイ）が導入前比で+15ポイント以上向上する

## 2. 基本原則と制約

### 2.1 開発原則

1. **仕様を唯一の情報源とする** — すべての実装判断は仕様書に基づく
2. **Why と What を仕様に書く** — How（実装方法）はコードに委ねる
3. **変更は仕様から始める** — コードより先に仕様を更新する
4. **AI出力は人間がレビューする** — 最終責任は必ず人間が負う

### 2.2 技術的制約

| 制約項目 | 内容 | 理由 |
|----------|------|------|
| フロントエンド | TypeScript + Vue.js 3 + Nuxt.js 3 (SSR) | エンタープライズ実績・SSRによるセキュリティ向上 |
| バックエンド | ASP.NET Core 8 (C#) + Web API | 金融系日本企業での実績・型安全性・保守性 |
| ORM | Entity Framework Core 8 | .NET標準・マイグレーション管理が容易 |
| データベース | Azure SQL Database | 金融グレードのSLA・Azure標準 |
| 認証 | Microsoft Entra ID（旧Azure AD） | 社内SSO・MFA・ロールベースアクセス制御 |
| インフラ | Azure Container Apps + WAF | マネージドコンテナ・OWASPセキュリティ対策 |
| シークレット管理 | Azure Key Vault | 接続文字列・APIキーのセキュア管理 |
| 監視 | Azure Monitor + Application Insights | 金融系要件の監査ログ・パフォーマンス監視 |
| データ保護 | 個人情報保護法・社内情報セキュリティ規程に準拠 | 評価データは機微情報として扱う |

### 2.3 ビジネス制約

- **期限**: 2027-02-28（リリース目標）
- **予算**: 要確認
- **法規制**: 個人情報保護法・労働基準法（評価・考課に関わる記録保持義務）・社内情報セキュリティ規程
- **データ保持期間**: 評価・考課データは7年保持（労働基準法第109条準拠）
- **その他**: 金融系グループ会社のコンプライアンス要件に準拠すること

## 4. 変更管理ルール

### 4.1 仕様変更のプロセス

```
変更要求 → Issue 作成 → 関係者レビュー → 承認 → 仕様書更新 → コード反映
```

1. **変更要求**: GitHub Issue を作成し `spec-change` ラベルを付ける
2. **影響範囲確認**: 関連仕様書・タスク・コードへの影響を Issue に記載
3. **承認**: 変更規模に応じた承認者のレビューを取得
4. **仕様書更新**: 先に仕様書を更新し PR を作成
5. **コード反映**: 仕様変更 PR マージ後に実装 PR を作成

### 4.2 変更規模と承認権限

| 変更規模 | 定義 | 必要な承認者 |
|----------|------|-------------|
| マイナー | 誤字修正・表現の明確化（機能変更なし） | テックリード |
| スモール | 既存機能の小規模な変更 | PM + テックリード ※PM未定期間は @KokiTokutake 単独承認で可 |
| メジャー | 新機能追加・既存機能の大規模変更 | PO + PM + テックリード ※PO/TL兼任のため @KokiTokutake + PM の2者承認 |
| 憲章変更 | この文書自体の変更 | 全ステークホルダー |

### 4.3 この憲章の変更

この憲章の変更は 原則決定工程（Constitution process）を経て行う。
緊急変更であっても、事後に全ステークホルダーの追認を得ること。

## 5. ワークフロー定義

### 5.1 ブランチ戦略

```
main ─────────────────────────────── （本番）
  └── spec/[issue番号]-[機能名]      （仕様書変更）
  └── feat/[issue番号]-[機能名]      （機能実装）
  └── fix/[issue番号]-[内容]         （バグ修正）
  └── docs/[issue番号]-[内容]        （ドキュメント）
```

### 5.2 Issue ラベル定義

| ラベル | 用途 |
|--------|------|
| `spec-change` | 仕様書の変更を伴う |
| `constitution-change` | 憲章の変更を伴う |
| `bug` | 仕様との不一致（バグ） |
| `enhancement` | 機能追加・改善 |
| `question` | 仕様の解釈に関する質問 |

## 6. 用語集（ユビキタス言語）

> チーム内で共通の意味を持つ用語を定義します。
> 曖昧さを排除し、仕様書・コード・会話で統一した言葉を使います。

| 用語 | 定義 | 使用例 |
|------|------|--------|
| タレント | 評価・管理の対象となる社内ITエンジニア | 「タレントのスキルを登録する」 |
| 考課 | 人事評価のプロセス全体（目標設定〜最終評価〜フィードバック） | 「通期考課フロー」 |
| Will-Can-Must | リクルート発のキャリア開発フレームワーク（やりたい・できる・やるべき） | 「WillとMustのギャップを埋める」 |
| 重点管理人物 | 組織として育成・支援を集中させると決定したエンジニア | 「人材開発委員会で重点管理人物を選定」 |
| 人材開発委員会 | 重点管理・育成方針を審議する定期会議体 | 「Q2人材開発委員会の議事録」 |
| アセスメント | スキル・能力の評価・測定結果 | 「技術アセスメントを実施」 |
| キャリアプラン | タレントの中長期的な成長・ポジション目標 | 「3年後のキャリアプランを策定」 |
| 上長 | タレントを直接評価する直属の管理者。考課フローの第一評価者 | 「上長が自己評価を確認する」 |
| 管理職 | 上長の上位承認者。考課フローの第二承認者 | 「管理職が上長評価を承認する」 |
| 幹部長 | 考課フローの最終承認者（最上位） | 「幹部長が最終承認を行う」 |
| 管理者 | 人事評価チームが担うシステム管理者ロール。全タレントの考課状況を横断的に参照・管理できる | 「管理者が考課ステータスを一覧確認する」 |
