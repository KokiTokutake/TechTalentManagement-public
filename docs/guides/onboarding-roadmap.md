# 仕様駆動開発 導入ロードマップ

> このロードマップは、仕様駆動開発（SDD）をチームに導入するための段階的な計画です。
> 組織の規模・状況に応じてカスタマイズして使用してください。

---

## 全体像

```
PHASE 1        PHASE 2        PHASE 3        PHASE 4        PHASE 5
当日〜3日  →  1週間以内  →  1ヶ月以内  →  3ヶ月以内  →  6〜12ヶ月

基盤整備      ワークフロー    プロセス定着    自動化・計測    全体展開
```

---

## PHASE 1: 基盤整備（当日〜3日）

**ゴール**: チームが仕様駆動開発を始められる最低限の環境を整える。

### アクション

| # | アクション | 担当 | 完了条件 |
|---|-----------|------|---------|
| 1 | リポジトリを作成し、ハーネステンプレートをコピー | テックリード | `git push origin main` 完了 |
| 2 | `Constitution.md` の初版を作成 | テックリード + PO | チーム全員がレビュー・承認 |
| 3 | AI エディタ（Claude Code CLI / Codex）のセットアップ | 各開発者 | `claude --version` でバージョン確認 |
| 4 | ツールのセットアップガイドをチームに共有 | テックリード | 全員がコマンドを実行できる状態 |
| 5 | キックオフミーティングで SDD の目的・7工程を共有 | マネージャー | チーム全員が概念を理解 |

### 成果物

- [ ] GitHubリポジトリ（ハーネステンプレート適用済み）
- [ ] `Constitution.md` 初版
- [ ] チームメンバー全員の開発環境セットアップ完了

---

## PHASE 2: ワークフロー確立（1週間以内）

**ゴール**: 最初のPRを仕様書駆動で完成させる。

### アクション

| # | アクション | 担当 | 完了条件 |
|---|-----------|------|---------|
| 1 | Branch Protection Rules を設定 | テックリード | 直接プッシュが禁止されていることを確認 |
| 2 | CODEOWNERS を設定 | テックリード | テストPRでレビュー依頼が届くことを確認 |
| 3 | Issue / PR テンプレートを設定 | テックリード | テンプレートが表示されることを確認 |
| 4 | 最初の機能仕様書（`docs/spec/`）を作成 | 開発者 + PO | 受入基準が明確に記述されている |
| 5 | 仕様書レビューの実施（5軸チェック） | 全員 | PR マージ完了 |
| 6 | 仕様書に基づいた最初の実装PRを作成 | 開発者 | テスト通過・仕様トレーサビリティ確認 |

### 成果物

- [ ] GitHub Branch Protection / CODEOWNERS 設定完了
- [ ] 最初の仕様書（spec/）PR マージ完了
- [ ] 最初の実装 PR マージ完了（仕様書と紐付き）
- [ ] チームメンバー全員がPRプロセスを経験

---

## PHASE 3: プロセス定着（1ヶ月以内）

**ゴール**: 仕様書ファーストの習慣をチームに根付かせる。

### アクション

| # | アクション | 担当 | 完了条件 |
|---|-----------|------|---------|
| 1 | 全新機能で仕様書を先に作成するルールを徹底 | マネージャー | PR テンプレートの仕様書リンク欄が空のPRをブロック |
| 2 | 週次のレビュー会でSDD遵守状況を確認 | テックリード | 仕様書なしのPRが0件 |
| 3 | AI活用のプロンプトパターンを共有 | テックリード | チームで共通プロンプトを使用 |
| 4 | 最初のレトロスペクティブを実施 | 全員 | KPT 記録・アクションアイテム設定 |
| 5 | 仕様書のステータス管理（draft/review/approved）を運用 | 開発者 | 全仕様書にステータスが記載 |

### 成果物

- [ ] `docs/spec/` に 3件以上の承認済み仕様書
- [ ] レトロスペクティブ記録（retrospective.md）
- [ ] チームのプロンプトパターン集（ai-workflow.md カスタマイズ済み）

### 定着度チェック

```
✅ 仕様書を先に書いてからコーディングしているか？
✅ PR に必ず仕様書への参照が含まれているか？
✅ バグ報告に仕様書との不一致が明記されているか？
✅ 仕様変更時は必ずコードより先に仕様書を更新しているか？
```

## PHASE 4: 自動化・計測（3ヶ月以内）

**ゴール**: CI/CD で仕様整合性を自動チェックし、メトリクスで改善を可視化する。

### アクション

| # | アクション | 担当 | 完了条件 |
|---|-----------|------|---------|
| 1 | CI パイプラインで仕様書フォーマットチェックを自動化 | テックリード | PRごとに自動チェックが走る |
| 2 | 仕様書ステータスの自動バリデーション | テックリード | `deprecated` 仕様書の実装が検出される |
| 3 | メトリクス収集開始（PR レビュー時間・バグ件数） | マネージャー | 毎スプリント数値を記録 |
| 4 | Constitution.md の初回改訂 | 全員 | 運用で得た知見を反映 |
| 5 | ガバナンスルール（アクセス権・承認フロー）の見直し | テックリード + マネージャー | 規模に応じた承認数を設定 |

### 成果物

- [ ] CI パイプライン（ci.yml）稼働中
- [ ] スプリントごとのメトリクスレポート
- [ ] 改訂済み Constitution.md（v2以降）

## PHASE 5: 全体展開（6〜12ヶ月）

**ゴール**: 組織全体への展開・新メンバーの即戦力化・監査対応。

### アクション

| # | アクション | 担当 | 完了条件 |
|---|-----------|------|---------|
| 1 | オンボーディングを SDD ドキュメントで完結できる体制確立 | テックリード | 新メンバーが1週間以内に最初のPRを出せる |

| 3 | 監査対応（Signed Commits・Rulesets）設定 | テックリード | コンプライアンス要件を満たす |
| 4 | 導入効果の測定・報告 | マネージャー | バグ削減率・レビュー時間短縮を数値化 |
| 5 | ハーネステンプレート自体の改善提案 | 全員 | テンプレートの改善PRを提出 |

### 成果物

- [ ] オンボーディングドキュメント（新メンバー向け）
- [ ] 導入効果レポート
- [ ] 次フェーズに向けた改善提案

## 規模別 推奨優先度

### 小規模（3〜5人）

```

  ✅ Constitution.md
  ✅ 仕様書テンプレート（feature-spec.md）
  ✅ PR テンプレート
  ✅ Branch Protection（承認1名）

任意（余力があれば）:
  △ CODEOWNERS（全員 → @tech-lead 1人でも可）
```

## よくある質問（FAQ）

### Q: Constitution.md は最初から完璧に作る必要がありますか？

A: No。まず1〜2ページの初版を作り、運用しながら育てることが重要です。完璧を目指すより、チームが合意できる内容から始めてください。

### Q: 全ての機能に仕様書が必要ですか？

A: 新機能・仕様変更は必須。バグ修正・スタイル修正・リファクタリングは仕様書不要（Issue + PR テンプレートで管理）。

### Q: 既存のプロジェクトにはどう導入しますか？

A: 新機能開発から段階的に導入し、既存コードの仕様書は優先度の高い領域から遡及的に作成します。

### Q: AIが生成した仕様書はそのまま使えますか？

A: Human-in-the-Loop 原則に従い、必ず人間がレビュー・修正してから承認してください。AIは草稿作成・レビューを支援するツールです。
