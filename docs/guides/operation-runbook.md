## 2. 通常デプロイ手順

```bash
# 1. リリースブランチの確認
git log main --oneline -10

# 2. ステージングでの動作確認
# → 受入確認チェックリスト（acceptance-checklist.md）を実施

# 3. 本番デプロイ（GitHub Actions）
# → GitHub の Actions タブから "Deploy to Production" ワークフローを手動実行
# → または: main ブランチへのマージで自動デプロイ

# 4. デプロイ後の確認
# → ヘルスチェックエンドポイントを確認
curl https://[domain]/health

# 5. 監視ダッシュボードでエラー率・レスポンスタイムを確認
```

### ロールバック手順

```bash
# 直前のバージョンにロールバック
# GitHub Actions の "Rollback" ワークフローを実行
# または: 直前のリリースタグをデプロイ
git tag --list 'v*' | sort -V | tail -5
```

## 3. 障害対応

### 3.1 アラートレベル定義

| レベル | 定義 | 初動時間 | 対応者 |
|--------|------|---------|--------|
| P1（Critical） | サービス全停止・データ損失 | 15分以内 | オンコール全員 |
| P2（High） | 主要機能が使えない | 30分以内 | テックリード |
| P3（Medium） | 一部機能に影響・回避策あり | 2時間以内 | 担当エンジニア |
| P4（Low） | 軽微・見た目の問題 | 翌営業日 | 担当エンジニア |

### 3.2 障害対応フロー

```
アラート検知
  │
  ▼
状況確認（ログ・監視ダッシュボード）
  │
  ├─ サービス停止？ → P1対応・全員召集・ロールバック検討
  │
  ├─ 主要機能障害？ → P2対応・テックリードにエスカレーション
  │
  └─ 軽微な問題？ → P3/P4対応・Issue 登録・通常対応
  
  │
  ▼
原因特定 → 修正 → デプロイ → 確認
  │
  ▼
事後レビュー（障害報告書の作成）
```

### 3.3 よくある障害と対処

| 症状 | 確認箇所 | 対処 |
|------|---------|------|
| API が 500 を返す | アプリケーションログ | [手順] |
| DB 接続エラー | DB ステータス・接続数 | [手順] |
| 認証が通らない | JWT 秘密鍵・有効期限 | [手順] |
| レスポンスが遅い | APM・スロークエリログ | [手順] |
| CI が失敗する | GitHub Actions ログ | [手順] |

## 5. 仕様書・ドキュメントの運用

SDD における運用フェーズの重要な責務：**仕様書を最新の状態に保つ**。

### 仕様変更が発生した場合

```
運用中に仕様変更が必要になった
  │
  ▼
GitHub Issue を作成（spec-change テンプレート）
  │
  ▼
仕様書を更新（spec/ PR）→ レビュー → マージ
  │
  ▼
コード修正（feat/ PR）→ レビュー → マージ
  │
  ▼
リリースノートに記載
```

### 定期的な仕様書メンテナンス

| 作業 | 頻度 | 内容 |
|------|------|------|
| 仕様書の実装整合性確認 | リリースごと | 実装と仕様書が一致しているか |
| deprecated 仕様の整理 | 四半期 | 不要な仕様書を `deprecated` に変更 |
| 用語集の更新 | 半期 | Constitution.md の用語集を見直す |
