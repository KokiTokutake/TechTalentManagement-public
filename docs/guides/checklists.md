# 仕様駆動開発 チェックリスト集

> 役割別・規模別・フェーズ別のチェックリストと、よくある問題のトラブルシューティングをまとめています。

---

## 役割別チェックリスト

### 開発者向けチェックリスト

#### 実装前
- [ ] 対象機能の仕様書（`docs/spec/`）を読んだ
- [ ] 仕様書のステータスが `approved` になっている
- [ ] 受入基準をすべて理解した
- [ ] 曖昧な点はオーナーに確認済み
- [ ] 関連する仕様書（依存・影響範囲）も確認した

#### 実装中
- [ ] 仕様書に書かれていない機能を勝手に追加していない
- [ ] AI 生成コードは自分でレビューしてから使用している
- [ ] テストを実装と並行して書いている
- [ ] 仕様書の受入基準に対応するテストケースが存在する

#### PR 作成前
- [ ] 全受入基準を満たしていることを確認した
- [ ] ローカルでテストが通過している
- [ ] PR テンプレートの仕様書リンクを記入した
- [ ] 仕様書との差異がある場合は理由を記載した
- [ ] セルフレビュー（diff 確認）を完了した

#### 仕様変更が必要と気づいたとき
- [ ] 勝手に解釈して実装しない
- [ ] Issue にコメントで報告した（`question` ラベル）
- [ ] 仕様書オーナーの判断を待っている
- [ ] 承認後に仕様書を更新してから実装を進める

---

### マネージャー向けチェックリスト

#### プロジェクト開始時
- [ ] `Constitution.md` の作成に参加した
- [ ] 仕様駆動開発の目的・プロセスをチームに説明した
- [ ] 仕様書ファーストのルールをチームに周知した
- [ ] 「仕様書なしの実装」をブロックする仕組みを整えた

#### 定常運用
- [ ] 自ら仕様書の草稿を書いている（または書けるようになっている）
- [ ] 仕様変更は必ずコードより先に仕様書に反映している
- [ ] PR レビューで「仕様書との整合性」を確認している
- [ ] ステークホルダーが仕様書をレビューできる環境を作っている

#### スプリント終了時
- [ ] 完了した機能の仕様書ステータスを更新した
- [ ] 次スプリントの機能に対して仕様書が `approved` になっている
- [ ] レトロスペクティブで SDD メトリクスを確認した

---

### 品質保証（QA）向けチェックリスト

#### テスト計画時
- [ ] 仕様書の受入基準を全件把握している
- [ ] 受入基準をテストケースとして列挙した
- [ ] テストケースが仕様書の Spec ID と紐付いている
- [ ] 境界値・異常系のテストを洗い出した

#### テスト実施時
- [ ] 受入チェックリスト（`acceptance-checklist.md`）を使用している
- [ ] 仕様書に書かれていない動作を「バグ」として報告している
- [ ] バグ報告に「仕様書との不一致」を明記している
- [ ] 仕様書の曖昧さを発見した場合は `question` ラベルで Issue 登録

#### リリース前
- [ ] 全受入基準の確認結果を記録した
- [ ] PO（プロダクトオーナー）の受入サインをもらった
- [ ] リリースノートと仕様書が一致していることを確認した

---

### 経営層・意思決定者向けチェックリスト

#### 導入決定時
- [ ] 仕様駆動開発の導入目的を明確に定めた（コスト削減・品質向上・スケール対応）
- [ ] 導入に必要なリソース（時間・人・ツール）を確保した
- [ ] 仕様書ファーストの文化をトップダウンで支持している

#### 運用中
- [ ] Constitution.md の変更に関与している（特に ビジネス原則）
- [ ] メトリクス（バグ削減率・開発速度）を定期的に確認している
- [ ] 「仕様書を書く時間」を開発プロセスの正式な工程として認めている

## フェーズ別チェックリスト

### 工程1: 原則決定工程（Constitution）

- [ ] プロジェクトの目的と価値を明文化した
- [ ] スコープ（含む / 含まない）を定義した
- [ ] 主要ステークホルダーと責任範囲を定義した
- [ ] 変更管理ルールを定めた（誰が承認するか）
- [ ] 用語集（ユビキタス言語）を作成した
- [ ] チーム全員が Constitution.md に合意・署名した

### 工程2: 企画・要件定義工程（Specify）

- [ ] 仕様書を `docs/spec/` に配置した
- [ ] Why（なぜ作るか）を明記した
- [ ] What（何を作るか）を明記した
- [ ] 受入基準（Given-When-Then）を記載した
- [ ] 優先度（Must / Should / Could）を設定した
- [ ] Spec ID を付与した（`SPEC-XXX-001` 形式）
- [ ] 5軸レビュー（明確性・完全性・一貫性・実装可能性・将来性）を実施した
- [ ] PR マージ後にステータスを `approved` に更新した

### 工程3: 設計計画工程（Plan）

- [ ] 仕様書のすべての要件が設計に反映されている
- [ ] 技術スタックの選択理由を記録した
- [ ] 不採用技術の理由も記録した（将来の意思決定のため）
- [ ] セキュリティ脅威と対策を設計書に記載した

### 工程4: タスク分割工程（Tasks）

- [ ] 1タスク = 1PR = 80分以内でレビュー完了できる粒度
- [ ] 各タスクに Spec ID と Issue 番号が紐付いている
- [ ] タスクに見積もり（ストーリーポイント）を設定した
- [ ] タスクの依存関係を整理した

### 工程5: 実装工程（Implement）

- [ ] コーディング前に仕様書を読んだ
- [ ] 実装が受入基準をすべて満たしている
- [ ] AI 生成コードを人間がレビューした
- [ ] テストと実装をセットでコミットした

### 工程6: 検証・受入工程（Verify / Accept）

- [ ] 受入チェックリストを使ってテストした
- [ ] 仕様書とコードのトレーサビリティを確認した
- [ ] PO が受入確認を完了した（サインした）
- [ ] テスト結果を記録した

### 工程7: 移行・運用工程（Migration / Operation）

- [ ] 運用ランブック（`operation-runbook.md`）を作成した
- [ ] モニタリング・アラート設定を完了した
- [ ] リリースノートを作成した
- [ ] レトロスペクティブを実施した
- [ ] 次サイクルへのフィードバックを記録した

## 規模別チェックリスト

### 小規模（3〜5人）の最低限セット

```
リポジトリ設定:
  ✅ Branch Protection（承認1名）
  ✅ PR テンプレート
  ✅ 基本的なIssueテンプレート

ドキュメント:
  ✅ Constitution.md（簡潔版 1〜2ページ）
  ✅ 機能仕様書テンプレート（feature-spec.md）
  ✅ README.md（プロジェクト概要 + セットアップ手順）

運用:
  ✅ 週次の簡易レトロスペクティブ
  ✅ 仕様書ファーストルールの口頭合意
```

### 中規模（6〜30人）の推奨セット

```
リポジトリ設定:
  ✅ 小規模の全項目
  ✅ Branch Protection（承認2名）
  ✅ CODEOWNERS（領域別）
  ✅ 全種類の Issue / PR テンプレート

ドキュメント:
  ✅ Constitution.md（詳細版）
  ✅ 機能仕様書 + API仕様書 + UI仕様書テンプレート
  ✅ アーキテクチャ設計書
  ✅ テスト計画・受入チェックリスト

自動化:
  ✅ CI パイプライン（仕様書フォーマットチェック + テスト自動実行）

運用:
  ✅ スプリントごとのレトロスペクティブ
  ✅ メトリクス計測（バグ件数・PR レビュー時間）
  ✅ 四半期ごとの Constitution.md 見直し
```

  ✅ GitHub Rulesets（高度なポリシー管理）
  ✅ CODEOWNERS（機能ドメイン単位）
  ✅ Organization Security Policy
  ✅ Secret Scanning 有効化

ドキュメント:
  ✅ Constitution.md（ドメイン別サブ憲章も検討）
  ✅ 機能ドメイン別 spec/ ディレクトリ構造
  ✅ オンボーディングドキュメント
  ✅ 監査対応ドキュメント

自動化:
  ✅ 中規模の全自動化
  ✅ Spec ID の存在確認自動チェック
  ✅ deprecated 仕様書の実装参照検出

運用:
  ✅ 月次の全体レトロスペクティブ
  ✅ 四半期ごとの監査レビュー
  ✅ SDD 推進チームの設置

## トラブルシューティング Q&A

### Q1: コードを変更したが仕様書が更新されない

**症状**: 実装は変わったが `docs/spec/` の内容が古いまま。

**原因**: 「仕様書を後で更新する」という先送り習慣。

**対処**:
1. PR テンプレートに「仕様書を更新した」チェックボックスを追加する
2. CI で `spec/` の最終更新日と実装ファイルの更新日を比較するチェックを追加する
3. レビュアーが仕様書の内容確認を必須化する（PR マージ要件）
4. レトロスペクティブでこの問題を Issue として挙げ、Try に対処策を入れる

---

### Q2: 仕様書のアクセス制限が入り組んで複雑になってきた

**症状**: CODEOWNERS や Branch Protection の設定が増え、誰がどのファイルを承認できるか不明瞭。

**原因**: 組織の成長に設定が追いついていない。

**対処**:
1. `docs/guides/github-setup.md` の規模別設定を参照し、現在の規模に合った設定に整理する
2. CODEOWNERS のコメントに「誰が・なぜこのファイルを管理するか」を記載する
3. 半期に一度、アクセス権限の棚卸しを実施する（`operation-runbook.md` 参照）

---

### Q3: AI が仕様書に書いていない機能を実装してしまった

**症状**: AI ツールが「便利そう」と判断した機能を勝手に追加する。

**対処**:
1. AI へのプロンプトに「仕様書に記載されていない機能は実装しないこと」を明記する
2. `templates/CLAUDE.md` の制約セクションにこのルールを追加する
3. PR レビューで「仕様書にない機能を発見したら差し戻す」ルールを徹底する

---

### Q4: 受入基準が曖昧でテストが書けない

**症状**: 仕様書の受入基準が「〜であること」という定性的な記述で、テストケースに落とし込めない。

**対処**:
1. 受入基準を Given-When-Then 形式で書き直す
2. AI に「この受入基準をテストケースに変換して」と依頼して具体化する
3. 仕様書レビュー時に「この基準はテストで確認できますか？」という問いを必須にする

---

### Q5: チームメンバーが仕様書を読まずに実装している

**症状**: PR レビューで「仕様書と違う」という指摘が多い。

**対処**:
1. PR テンプレートに「仕様書の受入基準を番号付きで引用した」チェックを必須化する
2. `CLAUDE.md` に「コーディング前に仕様書を読む」を最初のルールとして記載する
3. 1on1 やチームミーティングで SDD の「なぜ仕様書が必要か」を再共有する
4. AI ワークフローガイド（`ai-workflow.md`）の仕様書読み込みプロンプトを標準化する

---

### Q6: 仕様書が増えすぎて管理しきれない

**症状**: `docs/spec/` にファイルが増え、最新状態が把握しにくい。

**対処**:
1. `docs/spec/_README.md` にステータス一覧（approved / deprecated）を管理する
2. ディレクトリをドメイン単位で分割する（`docs/spec/auth/`, `docs/spec/payment/` 等）
3. 四半期ごとに `deprecated` 仕様書をアーカイブする
4. CI で `approved` 以外の仕様書が実装に参照されていないか自動チェックする

---

### Q7: Constitution.md を変更したいが誰が承認するか分からない

**症状**: 変更管理ルールが明確でなく、Constitution.md の改訂が止まっている。

**対処**:
1. Constitution.md の「変更管理ルール」セクションに承認者を明記する
2. 変更の大きさ（マイナー / スモール / メジャー / 憲章変更）に応じた承認プロセスを定める
3. CODEOWNERS で `.constitution/` に全ステークホルダーを指定する
