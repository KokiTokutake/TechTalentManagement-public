## 3. テスト種別と方針

### 3.1 ユニットテスト（自動）

| 項目 | 内容 |
|------|------|
| 対象 | 個別の関数・クラス |
| 実行タイミング | PR 作成時（CI 自動実行） |
| カバレッジ目標 | [例: 80%以上] |
| フレームワーク | [Jest / pytest / go test] |

**観点:**
- 正常系: 仕様書の要件通りに動作するか
- 異常系: 不正な入力に対して適切なエラーを返すか
- エッジケース: 境界値・空データ・最大値

### 3.2 統合テスト（自動）

| 項目 | 内容 |
|------|------|
| 対象 | API エンドポイント・DB との連携 |
| 実行タイミング | PR マージ時（staging 環境） |
| フレームワーク | [Supertest / httpx / net/http/httptest] |

**観点:**
- API の入出力が仕様書（api-spec.md）通りか
- エラーレスポンスの形式・ステータスコードが正しいか
- 認証・認可が正しく機能しているか

### 3.3 受入テスト（手動）

| 項目 | 内容 |
|------|------|
| 対象 | 仕様書の受入基準 |
| 実行タイミング | ステージング環境でのリリース前 |
| 担当 | QA / PO / ステークホルダー |

**観点:**
- 仕様書の受入基準を一つひとつ満たしているか
- ユーザー視点で自然に使えるか
- 仕様書に書かれていない挙動がないか

### 3.4 回帰テスト（自動）

| 項目 | 内容 |
|------|------|
| 対象 | 既存機能への影響確認 |
| 実行タイミング | PR マージ時（自動） |
| 方針 | 全ユニット・統合テストを実行 |

## 6. 完了基準（リリース判定）

以下をすべて満たした場合にリリース可とする：

- [ ] ユニットテストのカバレッジが目標値（[N]%）以上
- [ ] 全自動テストが通過（CI グリーン）
- [ ] 全受入テストケースが合格
- [ ] High 優先度のバグがゼロ
- [ ] PO / ステークホルダーの最終承認

---

## 7. バグ報告

発見したバグは GitHub Issue（`bug-report` テンプレート）で報告する。

| 深刻度 | 定義 | リリースへの影響 |
|--------|------|--------------|
| Critical | サービス停止・データ損失 | リリース不可 |
| High | 主要機能が使えない | リリース不可 |
| Medium | 一部機能に影響・回避策あり | 要判断 |
| Low | 軽微・見た目の問題 | 次回対応可 |
