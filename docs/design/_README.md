# 設計ドキュメント（Design）ディレクトリ

設計計画工程（Plan）の成果物を格納するディレクトリです。
仕様書（`docs/spec/`）の「What」を受け取り、「How」を設計します。

## テンプレートの選び方

| テンプレート | 用途 | 作成タイミング |
|-------------|------|-------------|
| `architecture.md` | システム全体の技術設計・アーキテクチャ | プロジェクト開始時・大規模変更時 |
| `component-design.md` | 個別コンポーネントの詳細設計 | 実装前（コンポーネントごと） |

## 設計書と仕様書の関係

```
仕様書（docs/spec/）    設計書（docs/design/）
  ─────────────────       ──────────────────────
  Why（なぜ）      →      技術選定の理由
  What（何を）     →      アーキテクチャ・データモデル
  受入基準         →      テスト戦略・検証方法
```

## 設計書を書くときのルール

### 必ず記載すること
- **技術選定理由**: 「なぜその技術を選んだか」と「何を却下したか」
- **仕様書との対応**: どの Spec ID の要件を満たすための設計か
- **制約**: Constitution.md の技術制約との整合性

### 設計書に書かない（コードに委ねる）こと
- 変数名・関数名などの命名規則の細部
- 具体的なアルゴリズムの実装詳細（コメントに書く）
- コードスタイル・フォーマット（linter に委ねる）

## AIを活用した設計のコツ

設計計画工程では、AIを「設計のたたき台作成」に活用できます。

1. **前提を渡す**: Constitution.md・仕様書・アーキテクチャ図を読ませる
2. **選択肢を生成させる**: 「この仕様を実現する設計を3案提示して」
3. **トレードオフを聞く**: 「各案のメリット・デメリットを比較して」
4. **人間が判断する**: 最終的な技術選択は必ず人間が行う
5. **ドキュメントに残す**: 却下した案と理由も含めて記録する

## ファイル命名規則

```
architecture.md                 # システム全体設計（1プロジェクト1ファイル）
[component-name]-design.md      # コンポーネント設計
diagrams/                       # 図ファイル（draw.io, Mermaid等）
  architecture.drawio
  [component]-flow.md
```
