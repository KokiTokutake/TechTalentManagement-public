## 1. 背景・目的（Why）

### 1.1 課題・背景

現在、エンジニアの評価・考課は Excel や紙ベースで運用されており、以下の問題が生じている。

- **集計・共有コストが高い**: 期末に各評価シートを手動で集計・配布しており、担当者の工数を圧迫している
- **承認フローが属人化している**: 誰が・いつ・どの段階で承認するかが明文化されておらず、担当者の記憶に依存している
- **履歴が参照できない**: 過去期の評価・フィードバックが一元管理されておらず、成長の振り返りに使えない
- **評価の納得感が低い**: フィードバックが書面で一方的に伝えられるだけで、対話・確認の機会が少ない

### 1.2 解決する価値

本機能によって以下の価値を提供する。

- **タレント**: 自分の目標・評価・フィードバックをいつでも参照でき、成長の軌跡が見える
- **上長**: 部下の目標・自己評価を一覧で確認でき、評価入力・承認操作をシステム上で完結できる
- **組織**: 全エンジニアの考課ステータスをリアルタイムで把握でき、滞留・未承認を早期発見できる

Constitution.md との対応:
- 成功定義「考課ワークフローが完全にデジタル化され、紙・Excelが不要になる」
- 成功定義「エンジニアの評価納得度が導入前比+15ポイント以上向上する」

### 1.3 スコープ外（やらないこと）

- 給与・報酬評価システムとの連携（考課データは本システム内で完結）
- 360度評価（同僚・部下からの評価）— v2以降の検討事項
- メール通知・外部メッセージング連携 — v2以降の検討事項
- スキルアセスメントとの自動連携 — v2以降の検討事項

## 2. 要件（What）

### 2.1 機能要件

#### ユーザーストーリー

```
As a タレント（評価対象エンジニア）,
I want to 期初に自分の目標を登録し、期末に自己評価を入力できる,
So that 上長からのフィードバックを受け取り、自分の成長を確認できる.

As a 上長,
I want to 担当タレントの自己評価を確認し、評価コメントを入力して承認できる,
So that 評価の承認フローを漏れなく・透明性を持って完了できる.

As a 管理職 / 幹部長,
I want to 自分の承認待ち一覧を確認し、承認・差し戻しができる,
So that 組織全体の考課フローを適切に進められる.
```

#### 要件一覧

| ID | 要件 | 優先度 | 備考 |
|----|------|--------|------|
| REQ-01 | タレントは期初に「目標」を登録できる（Will-Can-Must の各軸で入力） | Must | |
| REQ-02 | タレントは期末に「自己評価」を入力できる（目標ごとの達成度・コメント） | Must | |
| REQ-03 | 上長はタレントの自己評価を確認し、「上長評価」とコメントを入力できる | Must | |
| REQ-04 | 上長評価の入力後、承認ワークフロー（上長→管理職→幹部長）が自動的に開始される | Must | |
| REQ-05 | 各承認者は「承認」または「差し戻し」を選択でき、差し戻し時はコメントが必須 | Must | |
| REQ-06 | 全段階の承認完了後、タレントは評価・フィードバックを参照できる（開示） | Must | |
| REQ-07 | 期中に上長はタレントへの中間フィードバックを記録できる | Must | |
| REQ-08 | 考課フローの各ステップで、次のアクション担当者にシステム内アラートが通知される | Should | |
| REQ-09 | 管理者は全タレントの考課ステータス（未着手/進行中/承認待ち/完了）を一覧で確認できる | Should | |
| REQ-10 | 過去期の評価・フィードバック履歴を参照できる | Should | |
| REQ-11 | 考課期間（目標登録期限・評価入力期限・承認期限）を設定・管理できる | Should | |
| REQ-12 | タレントは承認完了後にフィードバックへのリアクション（確認済み）を記録できる | Could | |

> **優先度の定義**
> - **Must**: 必須。これがなければリリースしない
> - **Should**: 重要。可能な限り含める
> - **Could**: あれば望ましい。時間があれば対応

### 2.2 非機能要件

| 項目 | 要件 | 理由 |
|------|------|------|
| パフォーマンス | 一覧画面の初期表示 2秒以内、評価入力保存 1秒以内 | 入力中のストレス軽減 |
| セキュリティ | 自分の評価データのみ参照可能（上長は担当タレントのみ）。ログへの評価内容出力禁止 | 評価データは機微情報 |
| 可用性 | 考課期末の2週間は99.9%以上（ピーク時の入力集中に対応） | 期末に入力できないと業務が止まる |
| 監査ログ | 誰が・いつ・どの評価を・どう操作したかをすべて記録（7年保持） | 労働基準法第109条準拠 |
| アクセシビリティ | WCAG 2.1 AA 準拠 | 社内システムの標準要件 |

### 2.3 制約条件

- **ビジネス制約**: 考課は通期（1月〜12月）で1回/年。期の区切りはシステム設定で変更可能にすること
- **技術制約**: 認証は Microsoft Entra ID（SSO）を使用。評価データは Azure SQL Database に保存
- **法規制**: 評価・考課データは個人情報として取り扱い、7年間保持後に廃棄

## 3. 実装の境界（How の境界）

### 3.1 実装上の注意事項

- 評価データ（目標・評価コメント・評価点）はログに出力しないこと（機微情報のため）
- 承認フローの順序はシステムが強制する（上長承認なしに管理職承認はできない）
- 差し戻し時は、どのステップまで戻るかを明確に定義すること（仕様確定前に別途協議）

### 3.2 利用制約

- **前提条件**: ユーザーが Entra ID でログイン済みであること
- **依存仕様**: なし（本仕様が最初の機能仕様）
- **利用不可なケース**: 承認フロー進行中は、すでに承認済みのステップを編集できない

## 4. 受入基準（Acceptance Criteria）

```gherkin
# --- 目標設定 ---

Scenario: タレントが期初に目標を登録する
  Given タレントがログイン済みであり、当期の目標登録期間内である
  When  「目標設定」画面から Will / Can / Must の各軸で目標を入力し保存する
  Then  目標が保存され、上長の担当タレント一覧に目標登録済みとして表示される

Scenario: 目標登録期間外に目標を登録しようとする
  Given タレントがログイン済みであるが、目標登録期間が終了している
  When  「目標設定」画面を開く
  Then  「登録期間が終了しています」と表示され、入力フォームは非活性となる

# --- 中間レビュー ---

Scenario: 上長が期中に中間フィードバックを記録する
  Given 上長がログイン済みであり、担当タレントの目標が登録されている
  When  担当タレントの「中間レビュー」画面からコメントを入力し保存する
  Then  中間フィードバックが記録され、タレントがシステム内で参照できる

# --- 自己評価 ---

Scenario: タレントが期末に自己評価を入力する
  Given タレントがログイン済みであり、評価入力期間内であり、目標が登録済みである
  When  目標ごとに達成度（5段階）とコメントを入力し「自己評価を提出」する
  Then  自己評価が上長に提出され、タレント側は内容が読み取り専用になる

# --- 上長評価 ---

Scenario: 上長が自己評価を確認して上長評価を入力する
  Given 上長がログイン済みであり、担当タレントが自己評価を提出済みである
  When  タレントの自己評価を確認し、上長評価（5段階）とフィードバックコメントを入力して「評価を確定」する
  Then  上長評価が確定し、承認ワークフローの第1ステップ（管理職への承認依頼）が開始される

# --- 層別承認 ---

Scenario: 管理職が上長評価を承認する
  Given 管理職がログイン済みであり、承認待ち一覧に対象タレントの評価がある
  When  評価内容を確認し「承認」する
  Then  承認が記録され、次のステップ（幹部長への承認依頼）へ進む

Scenario: 管理職が差し戻しを行う
  Given 管理職がログイン済みであり、承認待ち一覧に対象タレントの評価がある
  When  「差し戻し」を選択しコメントを入力して実行する
  Then  上長評価が差し戻し状態になり、上長にシステム内アラートが通知される
       かつ 差し戻しコメントが記録される

Scenario: 全段階の承認完了後にフィードバックが開示される
  Given 幹部長が最終承認を完了した
  When  承認が確定する
  Then  タレントがシステム内で自分の評価・フィードバックコメントを参照できるようになる
       かつ タレントにシステム内アラートが通知される

# --- アクセス制御 ---

Scenario: タレントが他のタレントの評価を参照しようとする
  Given タレントAがログイン済みである
  When  タレントBの評価ページに直接アクセスしようとする
  Then  403エラーが返却され、評価内容は表示されない
```

### チェックリスト

- [ ] 目標登録・編集・削除が正しく動作する
- [ ] 自己評価の提出後は編集不可になる
- [ ] 承認ワークフローが上長→管理職→幹部長の順に流れる
- [ ] 差し戻し時にコメントが必須で、差し戻し元に通知が届く
- [ ] 最終承認後にのみタレントにフィードバックが開示される
- [ ] 他のタレントの評価データにアクセスできない（403）
- [ ] 評価データの内容がアプリケーションログに出力されない
- [ ] 考課期間外の操作が適切にブロックされる
- [ ] 7年分の監査ログが記録されている（操作者・日時・操作内容）
