# 仕様書（Spec）ディレクトリ

このディレクトリはプロジェクトの **Spec-as-Code** の中心です。
すべての仕様書を Markdown で記述し、Git で管理します。

## テンプレートの選び方

| テンプレート | 用途 | ファイル名の例 |
|-------------|------|--------------|
| `feature-spec.md` | 機能全般の仕様 | `user-authentication.md` |
| `api-spec.md` | REST API の仕様 | `users-api.md` |
| `ui-spec.md` | 画面・UI の仕様 | `login-screen.md` |

## 新しい仕様書を作る手順

1. **Issue を作成する** — 仕様化する機能の Issue を GitHub で作成
2. **テンプレートをコピーする**
   ```bash
   cp docs/spec/feature-spec.md docs/spec/[機能名].md
   ```
3. **Why から書く** — 背景・目的セクションを最初に埋める
4. **AIに壁打ちしてもらう** — README.md や Constitution.md を読ませた上でレビュー依頼
5. **PR を作成する** — `spec/[issue番号]-[機能名]` ブランチで PR
6. **レビュー・承認** — CODEOWNERS に定義されたレビュアーが承認
7. **ステータスを `approved` に変更** — マージ後に更新

## 仕様書を書くときのルール

### 書くこと
- **Why（なぜ）**: この機能が必要な理由・背景
- **What（何を）**: 実現すること・要件
- **受入基準**: 「完成」の判断基準

### 書かないこと
- **How（どうやって）**: 実装方法はコードとコメントに委ねる
- ライブラリ名・フレームワーク名（制約として必要な場合を除く）
- 詳細なDB設計（設計ドキュメント `docs/design/` に書く）

## Spec ID の採番ルール

```
SPEC-[カテゴリ]-[連番]

例:
SPEC-AUTH-001   認証関連の仕様
SPEC-USER-001   ユーザー管理関連の仕様
SPEC-API-001    API仕様
SPEC-UI-001     UI仕様
```

## ステータス管理

| ステータス | 意味 |
|-----------|------|
| `draft` | 作成中・未レビュー |
| `review` | レビュー中 |
| `approved` | 承認済み（実装可能） |
| `deprecated` | 廃止済み |

## AIを活用した仕様書作成のコツ

1. **Markdown で書く** — AIが解釈しやすく、差分管理が容易
2. **最初にルールを伝える** — Constitution.md と関連仕様書を読ませてから依頼
3. **出力形式を指定する** — 「Markdown の表形式で」「Given-When-Then 形式で」
4. **反復する** — AI の出力をベースに人間が修正・精緻化する
5. **最終確認は人間が行う** — AI 出力を鵜呑みにしない
