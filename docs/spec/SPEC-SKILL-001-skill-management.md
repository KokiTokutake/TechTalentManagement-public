## 1. 背景・目的（Why）

### 1.1 課題・背景

現状、エンジニアのスキル・技術レベルに関して以下の問題が生じている。

- **組織として技術ポートフォリオが見えない**: 誰がどの技術を使えるか一元的に把握できず、アサインや採用判断の根拠データがない
- **エンジニア自身がスキルを整理できていない**: キャリアプランと紐づいた自分の強み・弱みを体系的に把握できていない
- **成長履歴が残らない**: レベルが上がった経緯や時期が記録されず、評価時に成長を可視化できない
- **社外スタンダードとの乖離**: 組織内の評価が世間の技術トレンドや水準と合っているか確認できない

### 1.2 解決する価値

- **タレント**: 自分のスキルを体系的に整理・記録でき、成長の軌跡が見える
- **上長**: 部下のスキルを一覧で確認でき、育成計画・アサインの根拠にできる
- **組織（Admin/Senior/Executive）**: 全エンジニアの技術ポートフォリオを俯瞰でき、採用・育成方針の意思決定に活用できる

Constitution.md との対応:
- スコープ「エンジニアのスキル・技術レベルの記録と管理」
- 成功定義「エンジニアが自分のスキル・目標・評価履歴を一元的に参照できる」

### 1.3 スコープ外（やらないこと）

- 給与・等級への自動反映（考課システムとのデータ参照は行うが、給与計算は対象外）
- スキル認定試験・外部資格とのAPI連携（v2以降）
- プロジェクトアサインとのマッチング自動表示（SPEC-PROJ-001 実装後に追加）
- プロジェクト技術スタックからのスキル自動採用（SPEC-PROJ-001 実装後に追加）
- 360度スキル評価（同僚からのスキル評価）— v2以降

## 2. 要件（What）

### 2.1 スキルレベルの定義

| レベル | 名称 | 定義 |
|--------|------|------|
| 1 | 知識あり | 学習経験あり。業務での使用経験はない |
| 2 | 学習中 | 業務経験あり（1年未満）または独学で習得中 |
| 3 | 実務可 | 独力で業務遂行可能（1年以上の実務経験） |
| 4 | 指導可 | 後輩・チームへの技術指導が可能 |
| 5 | エキスパート | 組織内で最高水準。社外発信・技術選定ができるレベル |

> **注記**: SPEC-SKILL-002 で ITSS（1〜7段階）ベースへの拡張が計画されている。移行時は SPEC-SKILL-002 の変換ルール（1→1, 2→2, 3→3, 4→5, 5→7）に従い既存データを変換する。移行完了まで本5段階定義が有効。

### 2.2 スキルカテゴリ（マスターデータ）

管理者が定義するカテゴリ例（初期データ）:

| カテゴリ | 例 |
|---------|-----|
| プログラミング言語 | C#, Java, TypeScript, Python, Go |
| フレームワーク | ASP.NET Core, Spring Boot, Vue.js, React, Django |
| インフラ・クラウド | Azure, AWS, Docker, Kubernetes, Terraform |
| データベース | SQL Server, PostgreSQL, MySQL, Redis, MongoDB |
| セキュリティ | OWASP, 暗号化, 認証設計 |
| ソフトスキル | レビュー, 設計, ドキュメント, プレゼン |

### 2.3 機能要件

#### ユーザーストーリー

```
As a タレント（エンジニア）
I want to 自分のスキルをカテゴリ別に登録・更新したい
So that 自分の強み・弱みを整理し、成長を記録できる

As a 上長（Manager）
I want to 部下のスキル一覧を閲覧・承認したい
So that 育成計画やアサインの判断に活用できる

As a 管理者（Admin）
I want to スキルカテゴリとスキル種別のマスターを管理したい
So that 組織全体で統一されたスキル定義を維持できる

As a 管理職以上（Senior/Executive/Admin）
I want to 全エンジニアのスキルマップを俯瞰したい
So that 組織の技術ポートフォリオを把握し、採用・育成方針を決定できる
```

#### Must（必須）

| ID | 要件 | 対象ロール |
|----|------|----------|
| REQ-01 | 自分のスキル一覧をカテゴリ別に閲覧できる | Talent, Manager, Senior, Executive, Admin |
| REQ-02 | スキルを追加できる（スキル種別・レベル・補足コメントを入力） | Talent |
| REQ-03 | 登録済みスキルのレベル・コメントを編集できる | Talent |
| REQ-04 | 登録済みスキルを削除できる | Talent |
| REQ-05 | 上長がタレントのスキル申告を承認・差し戻しできる | Manager |
| REQ-06 | スキルカテゴリ（大分類）のCRUDを管理できる | Admin |
| REQ-07 | スキル種別（個別スキル名）のCRUDを管理できる | Admin |
| REQ-08 | 組織全体のスキルマップ（エンジニア×スキル）を閲覧できる | Senior, Executive, Admin |
| REQ-10 | 承認済みスキルのみ組織スキルマップに反映される（申請中・差し戻しは非表示） | 全員 |

#### Should（推奨）

| ID | 要件 | 対象ロール |
|----|------|----------|
| REQ-09 | スキルのレベル変更履歴を時系列で閲覧できる | Talent, Manager |

#### Could（あれば）

| ID | 要件 | 対象ロール |
|----|------|----------|
| REQ-11 | スキルを検索・フィルタリングできる（スキルマップ上） | Senior, Executive, Admin |

## 3. 受入基準（Given-When-Then）

### REQ-01: スキル一覧閲覧

```
Given: ログイン済みのタレントがいる
When:  スキル管理ページを開く
Then:  自分が登録したスキルがカテゴリ別に一覧表示される
       各スキルにはスキル名・レベル（1〜5）・承認状態・補足コメントが表示される

Given: ログイン済みの上長がいる
When:  部下のスキル管理ページを開く
Then:  その部下のスキル一覧がカテゴリ別に表示される
```

### REQ-02: スキル追加

```
Given: タレントがスキル管理ページを開いている
When:  スキルを追加しようとして、スキル種別・レベル（1〜5）を選択して保存する
Then:  スキルが「申請中」状態で登録され、一覧に表示される
       上長に承認待ちであることが視覚的にわかる

Given: 同一スキルが既に登録されている
When:  同じスキル種別を再度追加しようとする
Then:  「既に登録されています」エラーが表示され、追加できない
```

### REQ-03: スキル編集

```
Given: タレントが「承認済み」または「申請中」のスキルを持っている
When:  レベルまたはコメントを変更して保存する
Then:  スキルが「申請中」状態に戻り、上長の再承認が必要になる

Given: タレントが「差し戻し」状態のスキルを持っている
When:  内容を修正して保存する
Then:  スキルが「申請中」状態に戻り、上長の再承認待ちになる
       差し戻し理由の表示は消える

Given: タレントが他のタレントのスキルを編集しようとしている
When:  編集操作のAPIリクエストが実行される
Then:  HTTP 403 が返り、編集できない
```

### REQ-04: スキル削除

```
Given: タレントが自分のスキルを削除しようとしている
When:  削除操作を実行する
Then:  確認ダイアログが表示され、「削除する」を選択すると即時削除される
       承認済みスキルを削除した場合、組織スキルマップから即時除去される

Given: タレントが他のタレントのスキルを削除しようとしている
When:  削除操作のAPIリクエストが実行される
Then:  HTTP 403 が返り、削除できない
```

### REQ-05: 上長承認

```
Given: 部下が「申請中」のスキルを持っている
When:  上長が承認操作を実行する
Then:  スキルの状態が「承認済み」になる
       組織スキルマップに反映される

Given: 部下が「申請中」のスキルを持っている
When:  上長が差し戻し操作を実行する（差し戻し理由コメントは必須）
Then:  スキルの状態が「差し戻し」になる
       タレントのスキル一覧に差し戻し理由が表示される

Given: 上長が自分の部下以外のスキルを承認しようとしている
When:  承認操作のAPIリクエストが実行される
Then:  HTTP 403 が返り、承認できない
```

### REQ-06〜07: マスター管理

```
Given: 管理者がログインしている
When:  スキルカテゴリを新規追加する（カテゴリ名を入力）
Then:  カテゴリが作成され、スキル追加フォームで選択できるようになる

Given: 管理者がログインしている
When:  スキル種別を新規追加する（カテゴリ選択・スキル名入力）
Then:  スキル種別が作成され、タレントがスキル追加時に選択できるようになる

Given: 1件以上のタレントが使用中のスキル種別がある
When:  管理者がそのスキル種別の削除操作を実行する
Then:  「使用中のスキルがあります」エラーが表示され、削除できない
```

### REQ-08: 組織スキルマップ

```
Given: 管理職以上のユーザーがログインしている
When:  組織スキルマップページを開く
Then:  全エンジニアとその承認済みスキル一覧がカテゴリ別に表示される
       各セルにはレベル（1〜5）が表示される
       スキルを持たないエンジニアのセルは空白または「-」で表示される
```

## 4. データモデル（概要）

```
SkillCategory（スキルカテゴリ）
  Id, Name, DisplayOrder, CreatedAt, UpdatedAt

SkillItem（スキル種別マスター）
  Id, CategoryId, Name, DisplayOrder, CreatedAt, UpdatedAt

UserSkill（ユーザースキル）
  Id, UserId, SkillItemId, Level(1-5), Comment, Status(Pending/Approved/Rejected),
  ApprovedBy(UserId), ApprovedAt, RejectedReason, CreatedAt, UpdatedAt

UserSkillHistory（スキル変更履歴）
  Id, UserSkillId, Level, Status, ChangedAt, ChangedBy
```

---

## 5. 非機能要件

- スキルマップは全エンジニア × 全スキルを表示するため、エンジニア50名・スキル100件程度でも3秒以内に表示できること
- スキルデータは評価データ同様に機微情報として扱い、ロールに応じたアクセス制御を適用すること
