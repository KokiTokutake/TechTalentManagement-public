# /review-patterns — レビュー指摘パターンの閲覧・検索

**使う場面**: 仕様書・設計書・実装を始める前。または「過去にこういう指摘があったか確認したい」とき。

---

## 目的

`docs/guides/review-patterns.md` に蓄積されたレビュー指摘パターンを
カテゴリ・キーワード・頻度で検索・表示し、既知の問題を事前に排除する。

---

## 実行手順

### STEP 1: DBの存在確認

`docs/guides/review-patterns.md` を読み込む。

存在しない場合:
```
⚠️ レビューパターンDBがまだありません。
先に /review-learn を実行してPRから学習してください。
```

### STEP 2: 表示モードの選択

```
どのように確認しますか？

1. 全パターン一覧（頻度順）
2. カテゴリで絞り込む
3. キーワード検索
4. 頻度ランキング TOP10
5. 最近追加されたパターン（直近30日）
6. 現在の作業に関連するパターン（自動判定）
```

### STEP 3: 表示

**モード1: 全パターン一覧（頻度順）**

```markdown
## レビュー指摘パターン一覧（頻度順）

| ID | カテゴリ | タイトル | 頻度 | 最終確認 |
|----|---------|---------|------|---------|
| ARCH-001 | architecture | レイヤー間の直接依存 | 5回 | 2024-03-15 |
| SEC-001  | security     | ログへの機密情報出力 | 3回 | 2024-03-15 |
| SPEC-001 | spec-quality | 受入基準が検証不可能 | 3回 | 2024-03-10 |
| TEST-001 | test         | ハッピーパスのみテスト | 2回 | 2024-03-08 |

詳細を見るパターンIDを入力してください（例: ARCH-001）、または [Enter] で終了:
```

**モード2: カテゴリ絞り込み**

```
カテゴリを選んでください:
1. architecture (3パターン / 12件)
2. security (2パターン / 5件)
3. spec-quality (4パターン / 8件)
4. data-model (1パターン / 2件)
5. api-design (1パターン / 3件)
6. test (2パターン / 4件)
7. implementation (1パターン / 3件)
8. documentation (0パターン)
```

**モード3: キーワード検索**

```
検索キーワード: パスワード

マッチしたパターン: 2件

[SEC-001] ログへの機密情報出力
  頻度: 3回 | キーワードマッチ: "パスワードがログに出力"

[SEC-003] パスワード平文保存
  頻度: 1回 | キーワードマッチ: "パスワードをハッシュ化せずに保存"
```

**モード4: TOP10**

```markdown
## 🔥 頻度ランキング TOP10

1. 🥇 [ARCH-001] レイヤー間の直接依存 ............. 5回
2. 🥈 [SPEC-001] 受入基準が検証不可能 ............. 3回
2. 🥈 [SEC-001]  ログへの機密情報出力 ............. 3回
4.    [TEST-001] ハッピーパスのみテスト ........... 2回
5.    [API-001]  エラーレスポンス形式の不統一 ..... 2回
...

→ このランキングを `/retro-run` に渡しますか？ (yes / no)
```

**モード6: 現在の作業に関連するパターン（自動判定）**

現在のブランチ名・直近の編集ファイル・Spec IDから自動判定する:

```bash
# 現在のブランチ確認
git branch --show-current

# 直近の変更ファイル
git diff --name-only HEAD
```

```
現在の作業: feat/auth-login（認証機能）

関連パターン（自動抽出）:

⚠️ [SEC-001] ログへの機密情報出力（頻度: 3回）
   → 認証機能でよく発生。パスワード・トークンをログに含めないよう注意

⚠️ [ARCH-001] レイヤー間の直接依存（頻度: 5回）
   → Controller から直接 Repository を呼ばないよう注意

💡 [TEST-001] ハッピーパスのみテスト（頻度: 2回）
   → 認証失敗・アカウントロック等のエラーケースも /test-write でカバーする
```

### STEP 4: 詳細表示

パターンIDを指定した場合、フル詳細を表示:

```markdown
## [ARCH-001] レイヤー間の直接依存

**カテゴリ**: architecture
**指摘頻度**: 5回（PR #12, #18, #24, #31, #45）
**最終確認**: 2024-03-15
**傾向**: 📈 増加中（前スプリント2回 → 今スプリント3回）

### 指摘コメント例
> "Controller から直接 Repository を呼んでいます。Service 層を経由してください"（PR #45）
> "この import は依存の逆転が起きています"（PR #31）

### 修正パターン
Before: UserController → UserRepository
After:  UserController → UserService → UserRepository

### 再発防止策
- 設計書にレイヤー依存関係図を必須記載する
- `/design-review` Agent A（アーキテクチャ）が自動検出
- 実装前に依存グラフを確認する

### 関連パターン
- [ARCH-002] 循環依存
- [ARCH-003] ドメインロジックの Controller 混入
```

## 仕様書・設計書作成時の事前チェック形式

`/spec-write` や `/design-create` から呼び出された場合、
関連パターンをチェックリスト形式で表示する:

```markdown
## ⚠️ 過去の指摘パターン（事前確認チェックリスト）

作業内容（認証機能）に関連するパターンが **3件** あります。

作成前に以下を確認してください:

- [ ] [SEC-001] ログに password / token / secret を含めない（頻度5回）
- [ ] [ARCH-001] Controller → Service → Repository のレイヤーを守る（頻度3回）
- [ ] [TEST-001] 認証失敗・ロックアウト等のエラーケースもテストに含める（頻度2回）

これらは過去のPRレビューで繰り返し指摘された内容です。
確認したら [Enter] で仕様書/設計書の作成を続けます。
```

---

## DBが空またはパターンが少ない場合

```
パターンDB: 3件（少ない状態）

まだ学習データが少ないため、精度が低い可能性があります。
/review-learn を実行してPRから追加学習することを推奨します。

それでも現在のパターンを確認しますか？ (yes / no)
```

---

## 関連スキル

```
/review-learn    → PRから新しいパターンを学習・DB更新
/spec-write      → 仕様書作成（パターン事前チェック付き）
/design-create   → 設計書作成（パターン事前チェック付き）
/impl-check      → 実装チェック（パターン照合付き）
/retro-run       → スプリント振り返りにパターン傾向を反映
```
