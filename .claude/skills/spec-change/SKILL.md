# /spec-change — 仕様変更申請の対話型処理

**使う場面**: 工程2・5（要件定義・実装中）。実装中に仕様の不備・矛盾を発見した、または要件変更の必要が生じたとき。コードを変更する前に必ず実行する。

---

## 目的

「コードより先に仕様書を更新する」原則を守りながら、仕様変更を安全に申請・管理する。
変更の影響範囲を分析し、ステークホルダーへの確認が必要な判断を明確にする。

---

## 実行手順

### STEP 1: 変更内容の確認

```
質問（まとめて聞く）:
1. どの仕様書（Spec ID）を変更しますか？
2. 現在の仕様でどんな問題が起きていますか？
3. どのように変更したいですか？
4. なぜその変更が必要ですか？（根拠）
```

### STEP 2: 変更規模の判定

Constitution.md の変更管理ルールに照らして変更規模を判定し、ユーザーに提示する:

| 規模 | 基準 | 必要な承認 |
|------|------|-----------|
| マイナー | 誤字・用語統一・説明の明確化 | テックリードのみ |
| スモール | 受入基準の追加・削除、非機能要件の調整 | PO + テックリード |
| メジャー | 要件の追加・削除、スコープ変更 | PO + テックリード + ステークホルダー |
| 憲章変更 | Constitution.md に影響する変更 | 全員 |

「この変更は [規模] に該当します。[承認者] の承認が必要です。進めますか？」と確認する。

### STEP 3: 影響範囲の分析

変更対象の仕様書に関連する以下を確認・表示する:

- 関連する他の仕様書（`関連仕様` セクション参照）
- 関連する設計ドキュメント（`docs/design/`）
- 関連するタスク（`tasks/task-list.md`）
- 実装済みコードへの影響

```
⚠️ 影響範囲分析:
- 関連仕様書: SPEC-PAY-001（影響あり）
- 設計書: architecture.md（更新が必要な可能性）
- タスク: TASK-023（着手前のため影響軽微）
- 実装済みコード: src/auth/ に変更が必要
```

### STEP 4: 変更前後の diff 生成

現在の仕様書内容と変更後の内容を diff 形式で示し、ユーザーに確認を求める。

```diff
- 受入基準: ログイン試行は制限なし
+ 受入基準: ログイン試行は5回失敗でアカウントをロックする（30分）
```

「この変更内容でよいですか？」と確認する。

### STEP 5: spec-change ブランチと PR の作成

ユーザーが承認したら:

```bash
# ブランチ作成
git checkout -b spec/[issue番号]-[変更概要]
```

**注意（hooks ガード対応）**: このプロジェクトでは approved 仕様書の直接編集を hooks でガードしています。
仕様書編集の前に、まずステータスを `under_review` に変更することで hooks のバイパス条件を満たします。

```bash
# ステータスを under_review に変更してから編集する（hooksが検知して許可する）
# STEP 1: status: approved → status: under_review に変更
# STEP 2: 変更内容を適用
# STEP 3: コミット
git add docs/spec/
git commit -m "change: SPEC-XXX-001 [変更概要]"

# PR 作成（GitHub CLI）
gh pr create \
  --title "spec: SPEC-XXX-001 [変更概要]" \
  --label "spec-change" \
  --template ".github/PULL_REQUEST_TEMPLATE/spec-change.md"
```

### STEP 6: 承認者への通知案内

```
📢 承認が必要な方:
  @po-handle（プロダクトオーナー）
  @tech-lead-handle（テックリード）

PR を作成しました。以下のコマンドでメンションできます:
  gh pr comment [PR番号] --body "@po-handle @tech-lead-handle レビューをお願いします"

承認後、コードの変更を行ってください（/impl-guide で実装を再開）
```

---

## 注意事項

- コードの変更は仕様書 PR がマージされてから行う（絶対に逆にしない）
- 「小さな変更だから口頭でOK」は禁止。必ずPRを通す
- 承認者が不在・緊急の場合でも最低限テックリードの承認を得る
