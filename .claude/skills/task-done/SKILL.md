# /task-done — タスク完了・PR 作成

**使う場面**: 工程5（実装）。実装が完了し、PR を作成してレビューに出すとき。

---

## 目的

受入基準の達成確認・PR の作成・タスクステータス更新を漏れなく実施し、
仕様書との整合性が担保された状態でレビューに出す。

---

## 実行手順

### STEP 0: ゲートチェック（必須・失敗時は即停止）

```bash
git branch --show-current
```

| 結果 | 対応 |
|------|------|
| `main` | **即時停止**。「mainブランチで実装しています。`/task-start [TASK-ID]` を実行してfeatureブランチで作業してください。PRを作成できません。」と表示し、STEP 1 以降を実行しない |
| `feat/...` など | 正常。STEP 1 へ進む |

> このゲートはユーザーが「続けて」と言っても通過させてはならない。
> ブランチを切らずに実装したコードはガバナンス上存在しないものとして扱う。

### STEP 1: 現在のブランチ・タスクの確認

現在のブランチ名からタスク ID を特定し、対応するタスク情報を表示する。

```
現在のブランチ: feat/T-012-user-skill-api
対応タスク: TASK-012（ユーザースキルCRUD API）
対応仕様書: SPEC-SKILL-001
```

### STEP 2: 受入基準のセルフチェック

仕様書の受入基準を一覧表示し、各項目を確認する:

```
📋 受入基準チェック（SPEC-SKILL-001）

以下を一つずつ確認してください:
[ ] Given: タレントが申請中状態でスキルを追加できる
[ ] Given: 同一スキルの重複追加を拒否する（409）
[ ] ...

全て ✅ になりましたか？
```

未確認の項目がある場合は「まだ実装されていない受入基準があります。実装を完了してから再度 /task-done を実行してください」と伝えて**停止する**。

### STEP 2.5: E2Eテストファイルの存在チェック（必須ゲート）

タスクに紐付く Spec ID に対して、以下のパスにテストファイルが存在するか確認する:

```
tests/e2e/[SPEC-ID]-*.spec.ts
```

**例:** SPEC-SKILL-001 なら `tests/e2e/SPEC-SKILL-001-*.spec.ts`

| 結果 | 対応 |
|------|------|
| テストファイルが存在し、内容が受入基準を網羅している | 正常。STEP 3 へ進む |
| テストファイルが存在しない | **即時停止**（下記） |
| `[DB]` / `[DB Migration]` タグのタスク | 免除条件を確認（下記） |

**テストファイルが存在しない場合:**
```
⛔ E2Eテストファイルが見つかりません。

  対象仕様書: [SPEC-ID]
  期待するパス: tests/e2e/[SPEC-ID]-[feature-name].spec.ts

PR を作成する前に E2E テストを作成してください:

  /test-write

テストが全通過してから、再度 /task-done を実行してください。
```

**`[DB]` / `[DB Migration]` タスクの免除条件:**
DBスキーマ・マイグレーションのみのタスクはE2Eテストの代わりに以下を確認する:
- `dotnet test` が全通過していること
- 対応するAPIタスク（次タスク）でE2Eテストを書く旨をPR本文に明記すること

> このゲートはユーザーが「スキップして」と言っても通過させてはならない。
> E2Eテストなしの状態は「受入基準が人間の目でしか確認できていない」ことを意味する。

### STEP 3: テストの確認

テストを自動実行して確認する（確認で止めない）:

```bash
# バックエンド
cd backend && dotnet test

# フロントエンド（テストファイルがある場合）
cd frontend && npm run test

# E2E テスト
cd frontend && npx playwright test
```

テストが失敗している場合は**停止する**。「テストが失敗しています。修正してから再度 /task-done を実行してください」と伝える。

### STEP 4: コードの最終確認

```bash
# 変更ファイルの確認
git diff --stat main

# 未コミットファイルの確認
git status
```

未コミットの変更がある場合は警告し、コミットするよう促す。

### STEP 5: PR の作成

```bash
gh pr create \
  --title "feat: [TASK-ID] [タスクタイトル]（SPEC-XXX-001）" \
  --body "..." \
  --label "enhancement"
```

PR の本文に以下を自動入力する:
- 対応 Spec ID とファイルパス
- 対応設計書パス（`docs/design/[SPEC-ID]-design.md`）
- 受入基準の転記（チェックリスト形式）
- E2Eテストファイルのパスとテスト数
- 変更ファイルのサマリー（`git diff --stat main` の結果）
- ユニット/統合テスト件数・全通過の記録

内容を表示してユーザーに確認してから実行する。

### STEP 6: レビュアーの設定

CODEOWNERS の設定に基づいてレビュアーを確認する。
ソロ開発の場合はスキップしてよい。

### STEP 7: タスクステータスの自動更新

確認なしに `tasks/task-list.md` の該当タスクを「進行中」→「✅ done」に更新する。

### STEP 8: CI確認・マージ確認

PR 作成後、以下を確認してからマージを提案する:

```bash
# CI の通過を確認
gh pr checks [PR番号]
```

| 結果 | 対応 |
|------|------|
| CI 全通過 | ユーザーに「マージしますか？」と確認する |
| CI 失敗 | 「CI が失敗しています。修正してから再度確認してください」と伝えて**停止する** |

**ユーザーが「マージする」と回答した場合のみ**、以下を実行する:

```bash
gh pr merge [PR番号] --squash --delete-branch
git checkout main
git pull origin main
```

> マージはユーザーの明示的な承認なしに実行してはならない。
> CI が通過していない状態でマージを提案してはならない。

### STEP 9: 完了報告

```
✅ マージ完了

PR: https://github.com/[org]/[repo]/pull/[番号]
ブランチ: feat/T-012-user-skill-api → main（スカッシュマージ・削除済み）
ユニットテスト: 85件 全通過
E2Eテスト: 6件 全通過（tests/e2e/SPEC-SKILL-001-skill-management.spec.ts）

次のアクション:
  /task-board でタスクの進捗を確認できます
  次のタスクは /task-start [TASK-ID] で開始してください
```

---

## 注意事項

- STEP 0 のゲートはいかなる場合も省略・バイパスしない
- STEP 2.5 のゲートはいかなる場合も省略・バイパスしない（`[DB]`免除条件を除く）
- テストが通過していない状態でPRを出さない・マージを提案しない
- 受入基準を全て確認してからPRを出す
- 仕様書に書いていない機能を追加していないか確認する
- マージは必ずユーザーの承認を得てから実行する
