# /spec-trace — 仕様トレーサビリティの確認

**使う場面**: 工程6（検証）。実装コードと仕様書の対応関係を確認したいとき。リリース前の最終チェックとして使う。

---

## 目的

「すべての仕様書の要件がコードに実装されているか」「コードに仕様書のない実装がないか」を
双方向で確認し、仕様とコードの乖離を検出する。

---

## 実行手順

### STEP 1: 確認対象の設定

「どの範囲でトレーサビリティを確認しますか？」と確認する:

1. 特定の Spec ID（例: `/spec-trace SPEC-AUTH-001`）
2. 今回のスプリント全体（`docs/spec/` の approved 仕様書）
3. プロジェクト全体

### STEP 2: 仕様書 → コードの確認（順方向）

各仕様書の要件に対してコードに実装が存在するかチェックする:

```markdown
### ✅ 仕様書 → コード（順方向チェック）

SPEC-AUTH-001: ログイン機能
  ✅ 要件1: ログイン API → src/auth/auth.controller.ts:45
  ✅ 要件2: パスワード検証 → src/auth/auth.service.ts:78
  ❌ 要件3: アカウントロック → 実装が見つかりません

SPEC-USER-001: ユーザープロフィール
  ✅ 要件1: プロフィール取得 API → src/user/user.controller.ts:23
  ✅ 要件2: プロフィール更新 API → src/user/user.controller.ts:56
```

### STEP 3: コード → 仕様書の確認（逆方向）

実装コードに仕様書のない機能がないかチェックする。
主要なエンドポイント・パブリック関数を確認する:

```markdown
### ⚠️ コード → 仕様書（逆方向チェック）

以下の実装に対応する仕様書が見つかりません:
  - POST /api/auth/refresh-token (src/auth/auth.controller.ts:89)
    → 仕様書に追加するか、実装を削除してください
  - GET /api/admin/users (src/admin/admin.controller.ts:12)
    → 仕様書に追加するか、実装を削除してください
```

### STEP 4: テストカバレッジとの照合

仕様書の受入基準ごとにテストが存在するか確認する:

```markdown
### テストカバレッジ（仕様書ベース）

SPEC-AUTH-001
  ✅ 受入基準1 → test/auth/auth.test.ts:23
  ✅ 受入基準2 → test/auth/auth.test.ts:45
  ❌ 受入基準3 → テストなし
```

### STEP 5: トレーサビリティレポートの出力

```markdown
## トレーサビリティレポート（YYYY-MM-DD）

### サマリー
| 項目 | 数 | 状態 |
|------|-----|------|
| 仕様書の要件 | 15件 | |
| コードで実装済み | 12件 | 80% |
| テスト済み | 11件 | 73% |
| 仕様書なし実装 | 2件 | ⚠️ 要確認 |

### 要対応
1. SPEC-AUTH-001 要件3: アカウントロック実装が見つかりません → 実装が必要
2. POST /api/auth/refresh-token: 仕様書なし → 仕様書を追加するか実装を削除

### リリース可否判定
❌ 未実装の要件があるためリリース不可
✅ 全要件実装済み。リリース可能
```

### STEP 6: 問題への対応

未実装の要件がある場合: 「タスクを追加しますか？（/tasks-plan）」と提案する
仕様書なし実装がある場合: 「仕様書を追加しますか？（/spec-write）または実装を削除しますか？」と確認する
