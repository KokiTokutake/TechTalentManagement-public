# /design-create — 設計ドキュメントの対話型作成

**使う場面**: 工程3（設計計画）。approved になった仕様書をもとに、アーキテクチャ・コンポーネント設計書を作成するとき。

---

## 目的

仕様書の要件を満たすシステム設計を対話型で整理し、`docs/design/` に設計ドキュメントを生成する。
技術的な意思決定の理由を記録し、将来の判断に活用できる資産にする。

---

## 実行手順

### STEP 0: レビューパターンの事前チェック（自動）

`docs/guides/review-patterns.md` が存在する場合、アーキテクチャ・セキュリティ・データモデル・API設計カテゴリのパターンを抽出して表示する:

```
📚 過去のレビュー指摘パターン（設計前確認）

設計作業に関連するパターンが N件 あります:

⚠️ [ARCH-001] レイヤー間の直接依存（頻度: 5回）
   → レイヤー依存関係図を設計書に必ず含めてください

⚠️ [SEC-001] ログへの機密情報出力（頻度: 3回）
   → セキュリティ設計でログ禁止フィールドの方針を定義してください

⚠️ [DATA-001] 外部キー制約の欠落（頻度: 2回）
   → ERD にすべての制約を明記してください

[Enter] で続行:
```

パターンDBが存在しない場合はこのSTEPをスキップする。

### STEP 1: 前提確認

`docs/spec/` の approved 仕様書一覧を表示し、どの仕様書を対象とした設計か確認する。
`.constitution/Constitution.md` を読み込み、技術的制約を把握する。

### STEP 2: 設計ドキュメントの種類を確認

```
どの設計書を作成しますか？

1. アーキテクチャ設計書（architecture.md）  ← システム全体
2. コンポーネント設計書（component-design.md）  ← 機能単位の詳細
3. 両方
```

### STEP 3: アーキテクチャ設計（選択した場合）

以下を順に質問して設計書を生成する:

**システム構成の確認**:
```
- フロントエンド・バックエンド・DBの構成は？
- マイクロサービス構成か、モノリスか？
- 外部サービス（API・認証・ストレージ）の依存は？
- デプロイ環境（AWS / GCP / Azure / オンプレミス）は？
```

**技術スタック選定の記録**:
```
採用する技術について「なぜ選んだか」と「何を検討して採用しなかったか」を必ず記録する。
（例）
採用: Next.js → 理由: SSR対応・チームの習熟度
不採用: Nuxt.js → 理由: React 経験者が多いため

この情報は将来の意思決定に不可欠。面倒でも記録する。
```

**セキュリティ設計**:
```
- 認証方式（JWT / セッション / OAuth）
- 主要なセキュリティ脅威と対策（OWASP Top 10 への対応）
- データ暗号化方針
```

### STEP 4: コンポーネント設計（選択した場合）

仕様書の各要件に対応するコンポーネントを設計する:

```
対象の仕様書（Spec ID）: ?
主要なコンポーネント（クラス・関数・モジュール）を教えてください
型定義・インターフェースはどのように設計しますか？
DB テーブル設計（カラム・型・制約）は？
エラーハンドリング方針は？
```

### STEP 5: 設計書の生成・確認

`docs/design/architecture.md` または `docs/design/component-design.md` テンプレートに情報を埋めて生成する。
全文を表示してユーザーに確認を求める。

### STEP 6: 仕様書との整合性チェック

生成した設計書が対象仕様書の全要件を網羅しているか確認する。
漏れがあれば「この要件が設計書に反映されていません」と指摘する。

---

## 出力ファイル

- `docs/design/architecture.md`（アーキテクチャ設計書）
- `docs/design/component-design.md`（コンポーネント設計書）
