# /design-create — 設計ドキュメントの対話型作成

**使う場面**: 工程3（設計計画）。approved になった仕様書をもとに、コンポーネント設計書を作成するとき。
`/task-start` の前に必ず実行する。

> ⛔ **設計書なしに `/task-start` を実行することはできない。**
> `task-start` は `docs/design/[SPEC-ID]-design.md` の存在 **かつ `ステータス: approved`** を確認し、どちらかが満たされなければ停止する。

> ⚠️ **設計書は `draft` で生成される。`/task-start` を実行するには STEP 5 で承認を完了させること。**

---

## 目的

仕様書の要件を満たすシステム設計を対話型で整理し、`docs/design/` に設計ドキュメントを生成する。
技術的な意思決定の理由を記録し、将来の判断に活用できる資産にする。

---

## 出力ファイルの命名規則

設計書はスペックごとに独立したファイルとして生成する:

```
docs/design/[SPEC-ID]-design.md
```

**例:**
- `docs/design/SPEC-MDC-002-design.md`（9ボックス評価の設計書）
- `docs/design/SPEC-SKILL-001-design.md`（スキル管理の設計書）

> 複数仕様書にまたがる場合: 主となる Spec ID のファイル名を使い、関連 Spec ID を冒頭に記載する。

---

## 実行手順

### STEP 0: レビューパターンの事前チェック（自動）

`docs/guides/review-patterns.md` が存在する場合、アーキテクチャ・セキュリティ・データモデル・API設計カテゴリのパターンを抽出して表示する。
パターンDBが存在しない場合はこのSTEPをスキップする。

### STEP 1: 対象仕様書の確認

引数として Spec ID を受け取る。`/design-create SPEC-MDC-002` のように呼び出す。
指定がない場合は approved ステータスの仕様書一覧を表示し、どれを対象とするか確認する。

対象仕様書と Constitution.md を読み込み、技術的制約・要件を把握する。

### STEP 2: 設計書の生成

以下のセクションを対話形式で埋める:

**① エンティティ・データモデル設計**
- 仕様書のデータモデル（概要）を実装レベルに具体化する
- プロパティの型・制約・デフォルト値を確定する
- エンティティ間のリレーション（外部キー・削除ルール）を定義する
- インデックス設計（検索パターンに基づく）

**② APIエンドポイント設計**
- 仕様書のエンドポイント概要を実装仕様に具体化する
- リクエスト/レスポンスのスキーマ（型定義）
- 認可ルール（ロール別アクセス制御）
- エラーレスポンスの形式・ステータスコード

**③ フロントエンドコンポーネント設計**（UIを含む仕様書の場合）
- ページ・コンポーネント構成
- Pinia ストアの設計（state / getters / actions）
- data-testid の定義（E2Eテストで使用するセレクター）

**④ 技術的判断の記録**
- 採用した設計パターンとその理由
- 検討したが採用しなかった選択肢とその理由

### STEP 3: 仕様書との整合性チェック

生成した設計書が対象仕様書の全受入基準を網羅しているか確認する。
漏れがあれば「この受入基準が設計に反映されていません」と指摘する。

### STEP 4: ファイル生成・確認

生成した設計書の全文を表示し「保存しますか？」と確認する。
保存先: `docs/design/[SPEC-ID]-design.md`

**ステータスは必ず `draft` で生成する。** `approved` で生成してはならない。

### STEP 5: 設計書レビュー・承認（必須ゲート）

ファイル保存後、以下を実施する:

**5-1. 仕様書との整合性レポートを表示する:**

```
📋 設計書レビュー: [SPEC-ID]-design.md

受入基準の網羅確認:
  ✅ AC-01-01: [受入基準の概要]
  ✅ AC-01-02: [受入基準の概要]
  ⚠️ AC-02-01: [設計に反映されていない受入基準]

指摘事項:
  - [あれば具体的な問題点と改善案]

問題がなければ「承認する」、修正が必要であれば修正内容を指示してください。
```

**5-2. ユーザーの承認を得てからステータスを `approved` に更新する:**

ユーザーが「承認する」「OK」「問題ない」等を回答した場合のみ、設計書の `ステータス` 行を `approved` に書き換える。

```markdown
| ステータス | approved |
```

ユーザーが修正を指示した場合は修正してから再度レビューを提示し、承認を待つ。

> このゲートはユーザーが「スキップして」「続けて」と言っても通過させてはならない。
> 承認なしに `approved` にしてはならない。承認なしでは `/task-start` が停止する。

## 2. API設計

### [エンドポイント名]

**リクエスト:**
```json
{
  "field": "type"
}
```

**レスポンス（200 OK）:**
```json
{
  "field": "type"
}
```

**エラーレスポンス:**
| ステータス | 条件 |
|-----------|------|
| 400 | バリデーションエラー |
| 403 | 権限なし |
| 404 | リソース未存在 |

**認可ルール:**
| ロール | 操作 |
|--------|------|
| Talent | 自分のデータのみ取得・更新 |
| Manager | 配下タレントのデータ閲覧・承認 |

## 3. フロントエンド設計（UIあり仕様書のみ）

### コンポーネント構成

```
pages/
  [feature]/
    index.vue      # 一覧ページ
    [id].vue       # 詳細ページ

components/
  [feature]/
    [Feature]List.vue
    [Feature]Form.vue
```

### data-testid 定義

| 要素 | data-testid | 用途 |
|------|-------------|------|
| 保存ボタン | `[feature]-save-button` | E2Eテストのセレクター |

### Pinia ストア設計

```typescript
// stores/[feature].ts
interface [Feature]State {
  items: [Type][];
  loading: boolean;
}
```

```
