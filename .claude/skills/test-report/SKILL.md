# /test-report — テスト結果レポートと仕様書への反映

**使う場面**: 工程5（実装）→ 工程6（検証・受入）の橋渡し。
テスト通過後に正式レポートを生成し、仕様書の受入基準に通過マークを付与する。

---

## 目的

テスト結果を仕様書・タスク・スプリントと紐付けた正式レポートを生成し、
PO レビュー（工程6）の判断材料を提供する。
CI の JSON 出力をそのまま使うので、手動集計が不要。

---

## 実行手順

### STEP 1: テスト結果の読み込み

`tests/reports/results.json` を読む。存在しない場合:
```
⚠️ tests/reports/results.json が見つかりません。
先に /test-run を実行してください。
```

### STEP 2: 仕様書との紐付け

テスト名から Spec ID と AC 番号を抽出し、仕様書と照合する。

抽出ルール:
- テストファイル名の `spec-xxx-yyy` 部分
- `test.describe` の先頭にある `SPEC-XXX-NNN:` 形式
- テストのコメント行 `// AC-N:` 形式

### STEP 3: 仕様書への結果書き戻し（任意）

「受入基準に通過マークを追記しますか？」と確認してから実施:

```markdown
## 受入基準

<!-- テスト結果は /test-report により自動更新 YYYY-MM-DD -->
- [x] ✅ Given 正しいメールとパスワード When ログインボタン押下 Then ダッシュボードへ遷移する
      *(テスト通過: 2024-01-20 / 1.2s)*
- [x] ✅ Given 誤ったパスワード When ログインボタン押下 Then エラーメッセージを表示する
      *(テスト通過: 2024-01-20 / 0.8s)*
- [ ] ❌ Given 5回連続失敗 When ログイン試行 Then 30分アカウントロックされる
      *(テスト失敗: TimeoutError — data-testid="lockout-message" 未検出)*
```

### STEP 4: 正式レポートの生成

`docs/guides/test-report-YYYY-MM-DD.md` に以下を出力する:

```markdown
# テストレポート — YYYY-MM-DD

## プロジェクト情報
| 項目 | 値 |
|------|-----|
| プロジェクト | [プロジェクト名] |
| スプリント | Sprint N |
| タスク | TASK-XXX |
| 実行者 | @handle |
| Playwright バージョン | X.X.X |
| 実行環境 | Chromium / Node.js X.X |

## 総合結果

| 項目 | 値 |
|------|-----|
| 総テスト数 | 8 |
| ✅ 通過 | 7 |
| ❌ 失敗 | 0 |
| ⚠️ スキップ | 1 |
| 実行時間合計 | 12.4s |
| **通過率** | **100%（スキップ除く）** |

## 仕様書別結果

### SPEC-AUTH-001: ログイン機能
**ステータス**: ✅ 全受入基準通過

| AC# | 受入基準 | 結果 | 実行時間 |
|-----|---------|------|---------|
| AC-1 | Given 正しい認証情報 When ログイン Then ダッシュボードへ | ✅ | 1.2s |
| AC-2 | Given 誤ったパスワード When ログイン Then エラー表示 | ✅ | 0.8s |
| AC-3 | Given 5回連続失敗 When ログイン Then ロック | ✅ | 2.1s |

### SPEC-DASH-001: ダッシュボード表示
**ステータス**: ✅ 全受入基準通過（スキップ1件あり）

| AC# | 受入基準 | 結果 | 実行時間 |
|-----|---------|------|---------|
| AC-1 | Given ログイン済み When アクセス Then KPI表示 | ✅ | 1.8s |
| AC-2 | Given 10件以上 When 表示 Then 最新10件のみ | ⚠️ skip | — |

## スキップしたテスト
| テスト | 理由 |
|--------|------|
| SPEC-DASH-001 AC-2 | `test.skip` — 機能は実装済みだが環境依存のデータ生成が未整備 |

## スクリーンショット
（全テスト通過のため撮影なし）

## 次のステップ
- [ ] /accept-run → PO による受入テスト
- [ ] /spec-trace → 仕様書と実装の対応確認
- [ ] スキップしたテストの整備（次スプリント対応）
```

### STEP 5: GitHub PR へのコメント追加（任意）

「PR にテスト結果をコメントしますか？」と確認してから実施:

```bash
gh pr comment [PR番号] --body "$(cat docs/guides/test-report-YYYY-MM-DD.md | head -40)"
```

### STEP 6: 工程6 への引き継ぎ確認

```
## 工程6（検証・受入）への引き継ぎ

通過率: 100%（スキップ除く）

/accept-run を実行して PO のサインオフに進みますか？ (yes / no / 先にスキップテストを整備する)
```

全テスト通過 or ユーザーが承認した場合 → `/accept-run` を実行するよう案内する。

---

## CI 結果の自動取得

GitHub Actions を使っている場合、結果ファイルのパスを確認:

```bash
# actions/upload-artifact でアップロードされたレポートを確認
gh run list --workflow=e2e-test.yml --limit 5
gh run download [run-id] --name playwright-report --dir tests/reports
```

## テスト品質の評価基準

| 通過率 | 評価 | 次のアクション |
|--------|------|--------------|
| 100% | 🟢 優秀 | /accept-run へ進む |
| 90〜99% | 🟡 良好 | 失敗原因を確認して判断 |
| 70〜89% | 🟠 要修正 | 実装修正後に再テスト |
| 〜69% | 🔴 要緊急対応 | /impl-guide で実装を見直す |

## 関連スキル

```
/test-write  → テストコード生成
/test-run    → テスト実行
/accept-run  → テスト通過後の PO 受入テスト
/spec-trace  → 仕様書と実装の対応確認
/retro-run   → テスト品質をスプリント振り返りに反映
```
