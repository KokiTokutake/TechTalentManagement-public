# /impl-check — 実装と仕様書の整合性チェック

**使う場面**: 工程5（実装）。PR 作成前、または実装が受入基準を満たしているか確認したいとき。

---

## 目的

実装コードが仕様書の受入基準をすべて満たしているか確認し、
PR レビューで指摘される前に問題を発見・修正する。

---

## 実行手順

### STEP 0: レビューパターンの事前チェック（自動）

`docs/guides/review-patterns.md` が存在する場合、実装・テストカテゴリのパターンを抽出して表示する:

```
📚 過去のレビュー指摘パターン（実装チェック前確認）

実装作業に関連するパターンが N件 あります:

⚠️ [TEST-001] ハッピーパスのみテスト（頻度: 4回）
   → エラーケース・境界値のテストが揃っているか確認してください

⚠️ [IMPL-001] マジックナンバー（頻度: 2回）
   → 数値リテラルは定数に切り出されているか確認してください

[Enter] で続行:
```

パターンDBが存在しない場合はこのSTEPをスキップする。

### STEP 1: チェック対象の特定

現在のブランチから対応タスク・仕様書を特定する。
特定できない場合は「Spec ID を教えてください」と確認する。

### STEP 2: 仕様書の受入基準を読み込む

対応する仕様書を読み込み、全受入基準を抽出する。

### STEP 3: 実装コードとの照合

変更されたファイルを確認し（`git diff main`）、各受入基準に対して:

1. 対応するコードが存在するか
2. 対応するテストが存在するか
3. テストが受入基準を正しく検証しているか

を確認する。

### STEP 4: チェック結果の表示

```markdown
## 実装チェック結果: SPEC-AUTH-001

### 受入基準 vs 実装

| # | 受入基準 | 実装 | テスト | 判定 |
|---|---------|------|--------|------|
| 1 | 正しい認証で 200 + JWT 返却 | ✅ auth.controller.ts L45 | ✅ auth.test.ts L23 | ✅ |
| 2 | 誤ったパスワードで 401 返却 | ✅ auth.service.ts L78 | ✅ auth.test.ts L45 | ✅ |
| 3 | 5回失敗でアカウントロック | ✅ auth.service.ts L112 | ❌ テストなし | ❌ |
| 4 | ロック状態で 423 返却 | ⚠️ 実装が見当たらない | ❌ テストなし | ❌ |

### 判定: ❌ PR 作成前に修正が必要

### 修正が必要な項目:
1. 受入基準3のテストコードを追加する
2. 受入基準4（ロック状態の 423 レスポンス）の実装を確認・追加する

### 仕様書に書かれていない実装（注意）:
- auth.controller.ts L89 に仕様書外の "remember_me" パラメータが含まれています
  → 仕様書に追加するか、実装から削除してください
```

### STEP 5: 修正支援

未実装・テスト漏れが見つかった場合:
- 「修正・追加しますか？」と確認する
- 「はい」の場合、不足している実装コードまたはテストコードを生成する
- 生成したコードはユーザーが確認してから採用する

### STEP 6: 全件OK の場合

```
✅ 全受入基準が満たされています

次のステップ:
  /task-done → PR を作成してレビューに出す
```

---

## 注意事項

- テストが存在しても内容が受入基準を正しく検証していない場合は ❌ と判定する
- 仕様書に書かれていない実装を発見した場合は必ずユーザーに報告する
- 「テストは後で書く」という判断を認めない。テストと実装はセット
