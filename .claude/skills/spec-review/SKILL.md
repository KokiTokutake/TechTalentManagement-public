# /spec-review — 仕様書の5軸レビュー

**使う場面**: 工程2（要件定義）。仕様書を作成・更新した後、approved にする前のレビュー。PR レビューの観点として使う。

---

## 目的

仕様書を「明確性・完全性・一貫性・実装可能性・将来性」の5軸で評価し、
コーディング前に仕様の問題を発見・修正する。

---

## 実行手順

### STEP 1: 対象仕様書の特定

引数として Spec ID またはファイルパスを受け取る。
指定がない場合は `docs/spec/` の仕様書一覧を表示し、どれをレビューするか確認する。

`/spec-review SPEC-AUTH-001` のように呼び出された場合は該当ファイルを読み込む。

### STEP 2: Constitution.md との照合

`.constitution/Constitution.md` を読み込み、仕様書が憲章の原則・制約に沿っているか確認する。

### STEP 3: 5軸レビューの実施

**軸1: 明確性（Clarity）**
- 曖昧な表現（「高速に」「使いやすく」「適切に」）を検出して指摘する
- 受入基準が Given-When-Then 形式または明確な条件で書かれているか確認する
- 数値で表現すべき基準が定性的なままになっていないか確認する

**軸2: 完全性（Completeness）**
- 必須セクション（Why / What / 受入基準 / 優先度 / Spec ID）が揃っているか確認する
- エラーケース・例外処理の仕様が記載されているか確認する
- スコープ外（作らないこと）が明記されているか確認する

**軸3: 一貫性（Consistency）**
- 用語集（Constitution.md）の語彙が一貫して使われているか確認する
- 他の関連仕様書（`関連仕様` セクション）と矛盾していないか確認する
- Spec ID の命名規則に沿っているか確認する

**軸4: 実装可能性（Feasibility）**
- 技術的に実現できる要件か評価する
- Must 要件のみで実装したとき、スプリント内に完了できる規模か確認する
- 依存関係（他 Spec・外部 API）が明示されているか確認する

**軸5: 将来性（Evolvability）**
- 将来の変更に対して開放的な設計になっているか確認する
- 「絶対にこれ以上変更しない」という過度な制約がないか確認する
- 廃止・移行の計画が必要な場合に記載されているか確認する

### STEP 4: レビュー結果の出力

```markdown
## 仕様書レビュー結果: SPEC-XXX-001

### 総合評価: ★★★★☆（5段階）

| 軸 | 評価 | コメント |
|----|------|---------|
| 明確性 | ★★★★☆ | ... |
| 完全性 | ★★★☆☆ | エラーケースの記載なし |
| 一貫性 | ★★★★★ | 問題なし |
| 実装可能性 | ★★★★☆ | ... |
| 将来性 | ★★★☆☆ | ... |

### ⚠️ 修正が必要な点（High）
1. [具体的な問題と改善案]

### △ 改善推奨（Medium）
1. [具体的な問題と改善案]

### ✅ 良い点
- [良い点]

### 承認判定
[ ] この仕様書は approved にできる
[x] 修正後に再レビューが必要
```

### STEP 5: 修正支援

「修正しますか？」と確認し、「はい」の場合は指摘箇所を具体的に書き直す案を提示する。
ユーザーが承認したらファイルを更新する。

### STEP 6: ステータス更新の提案

レビューが通過した場合:
```
仕様書のステータスを draft → approved に更新しますか？
```

---

## 注意事項

- 全ての指摘を修正する必要はない。Medium 以下は担当者の判断に委ねる
- レビュー後のコミットメッセージ: `update: SPEC-XXX-001 仕様書をレビュー反映`
