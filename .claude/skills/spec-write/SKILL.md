# /spec-write — 仕様書の対話型作成

**使う場面**: 工程2（要件定義）。新機能・変更要件の仕様書を作成するとき。コーディングを始める前に必ず実行する。

---

## 目的

「なぜ作るか（Why）」「何を作るか（What）」「どうなれば完成か（受入基準）」を対話型で整理し、
Spec ID 付きの仕様書ファイルを生成する。

---

## 実行手順

### STEP 0: レビューパターンの事前チェック（自動）

`docs/guides/review-patterns.md` が存在する場合、作成する機能名・カテゴリに関連するパターンを抽出して表示する:

```
📚 過去のレビュー指摘パターン（事前確認）

作業内容に関連するパターンが N件 あります:

⚠️ [SEC-001] ログへの機密情報出力（頻度: 3回）
   → 仕様の非機能要件に「ログ禁止フィールド」を明記してください

⚠️ [SPEC-001] 受入基準が検証不可能（頻度: 5回）
   → 「〜できること」ではなく Given-When-Then で具体的に書いてください

これらは過去のPRレビューで繰り返し指摘された内容です。
仕様書作成時に意識してください。[Enter] で続行:
```

パターンDBが存在しない場合はこのSTEPをスキップする。

### STEP 1: 仕様書の種類を確認

```
どの種類の仕様書を作成しますか？

1. 機能仕様書（feature-spec）  ← 最も一般的
2. API 仕様書（api-spec）
3. UI 仕様書（ui-spec）
```

ユーザーの選択に応じて対応するテンプレート（`docs/spec/`）を使用する。

### STEP 2: Spec ID の決定

`docs/spec/` ディレクトリを確認して既存の Spec ID 一覧を表示する。
次の番号を提案する。形式: `SPEC-[カテゴリ]-[3桁連番]`

```
カテゴリ例（ユーザーに確認する）:
AUTH / USER / PAY / DASH / API / UI / NOTIFY / REPORT
```

### STEP 3: Why（なぜ作るか）の整理

```
質問:
- この機能でどんな問題を解決しますか？
- ユーザーにとってどんな価値がありますか？
- 作らないとどんな影響がありますか？
- Constitution.md のどの原則・目標に対応しますか？
```

ユーザーの回答から「背景・目的・ビジネス価値」のセクションを生成する。

### STEP 4: What（何を作るか）の整理

```
質問:
- この機能で何ができるようになりますか？（主要機能）
- 誰が使いますか？（対象ユーザー）
- Must（必須） / Should（推奨） / Could（あれば） の優先度は？
- スコープ外（作らないこと）を明確にしてください
```

MoSCoW 優先度付きの要件リストを生成する。

### STEP 5: 受入基準（Given-When-Then）の生成

What の各要件に対して Given-When-Then 形式の受入基準を生成する。

```
例:
Given: ユーザーがログイン済みである
When:  「注文する」ボタンをクリックする
Then:  注文確認画面が表示され、注文番号が発行される
```

ユーザーに「この受入基準でテストできますか？」と確認する。
曖昧な場合は具体的な数値・状態に修正する。

### STEP 6: 関連情報の確認

```
質問:
- 関連する仕様書の Spec ID はありますか？
- 参照すべき GitHub Issue はありますか？
- 想定工数・期限はありますか？
```

### STEP 7: ファイル生成・確認

生成した仕様書の全文を表示し「保存しますか？」と確認する。
保存先: `docs/spec/[カテゴリ名]/[spec-id]-[feature-name].md` または `docs/spec/[spec-id]-[feature-name].md`

---

## 出力ファイル

- `docs/spec/[spec-id]-[name].md`（新規作成）

---

## 次のステップ

```
/spec-review     → 作成した仕様書を5軸レビュー
/tasks-plan      → 仕様書が approved になったらタスク分割
/review-patterns → 蓄積パターンを確認・検索
```
