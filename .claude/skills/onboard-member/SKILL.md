# /onboard-member — 新メンバーのオンボーディング

**使う場面**: 既存の SDD プロジェクトに新しいメンバーが参加するとき。プロジェクトの現状・ルール・ワークフローを一気に把握させる。

> `/sdd-start` は「プロジェクトへの SDD 初回導入」、このスキルは「既存プロジェクトへの人の追加」。

---

## 目的

新メンバーが「何を読めばいいか」「どう作業を始めるか」を迷わず把握できるよう、
プロジェクトの現状スナップショットとオンボーディングチェックリストを提供する。

---

## 実行手順

### STEP 1: 新メンバーの情報収集

以下を確認する:

```
1. 名前・GitHub ハンドル（@xxx）
2. 担当予定の領域（フロントエンド・バックエンド・インフラ 等）
3. SDD 経験の有無（初めて / 他プロジェクトで経験あり）
4. 今すぐアサインするタスクはあるか（ある場合: タスク ID）
```

### STEP 2: プロジェクト現状スナップショットの生成

以下のファイルを読み込んで現状をまとめる:

- `.constitution/Constitution.md` — プロジェクト憲章
- `CLAUDE.md` — 開発ルール・コマンド
- `docs/spec/` — 仕様書一覧とステータス
- `tasks/task-list.md` — タスク一覧と進捗

```markdown
## 📋 [プロジェクト名] オンボーディングガイド

作成日: [今日の日付]
対象メンバー: [名前]（[GitHub ハンドル]）

---

### プロジェクト概要
[Constitution.md の目的・スコープから抜粋]

### 現在のフェーズ
[スプリント番号 / 主要な進行中タスク]

### チーム構成
[Constitution.md のステークホルダーセクションから抜粋]

---

### 仕様書の現状（docs/spec/）

| Spec ID | タイトル | ステータス | 担当 |
|---------|---------|-----------|------|
| [一覧] |

---

### 進行中タスク（tasks/task-list.md）

| Task ID | タイトル | ステータス | 担当 | SP |
|---------|---------|-----------|------|----|
| [進行中のタスクのみ] |

---

### あなたに関係する担当領域: [担当領域]

関連仕様書:
- [担当領域に関連する Spec ID と タイトル]

---

### 必ず読むべきドキュメント（この順番で）

1. ✅ `.constitution/Constitution.md` — プロジェクトの基本原則・制約・用語集
2. ✅ `CLAUDE.md` — 開発ルール・必須手順・コマンド一覧
3. ✅ `docs/spec/[担当領域の仕様書]` — 担当機能の仕様書
4. ✅ `docs/guides/review-patterns.md` — 過去のレビュー指摘パターン（あれば）
```

### STEP 3: 開発環境セットアップのガイド

`CLAUDE.md` のコマンドセクションをもとに、環境構築手順を提示する:

```markdown
### 開発環境セットアップ

# リポジトリのクローン
git clone [リポジトリ URL]
cd [プロジェクト名]

# 依存関係のインストール
[CLAUDE.md のインストールコマンド]

# 開発サーバー起動確認
[CLAUDE.md の起動コマンド]

# テスト実行確認
[CLAUDE.md のテストコマンド]
```

### STEP 4: SDD ワークフローの説明

SDD 経験の有無に応じて説明を変える:

#### SDD 初めての場合

```
SDD（仕様駆動開発）の基本ルール:

1. 実装する前に必ず仕様書（docs/spec/）を確認する
2. 仕様書が approved でないものは実装してはならない
3. 実装は必ずブランチを作って行う（main への直接コミット禁止）
4. ブランチは /task-start で作成する（手動作成禁止）
5. PR を出す前に /test-write でテストを書く

作業の流れ:
  /task-start [TASK-ID]  → 実装 → /test-write → /test-run → /task-done

困ったときは:
  /sdd-skills  — 使えるスキル一覧
  /sdd-health  — プロジェクトの健全性チェック
```

#### SDD 経験ありの場合

```
このプロジェクト固有のルール（CLAUDE.md より）:

- ブランチ命名: feat/[issue番号]-[タスク概要] / feat/T-[タスク番号]-[タスク概要]
- 設計書（docs/design/）が approved でないと /task-start が通らない
- E2E テストは tests/e2e/ に [SPEC-ID]-[機能名].spec.ts 形式で作成
- [プロジェクト固有のルール]

/review-patterns  — 過去のレビュー指摘パターン（先に確認推奨）
```

### STEP 5: 最初のタスクの案内（任意）

STEP 1 でアサインタスクが指定されている場合:

```
✅ 最初のタスク: [TASK-ID] [タイトル]

関連仕様書: [Spec ID] — [パス]
担当者に設定: [GitHub ハンドル]

準備ができたら:
  /task-start [TASK-ID]
```

タスクが指定されていない場合:

```
タスクは未割り当てです。
チームリード（[テックリードのハンドル]）にアサインを確認してください。
準備ができたら /task-start を実行してください。
```

### STEP 6: メンバー情報の記録

Constitution.md のステークホルダーセクションに新メンバーを追加するよう案内する:

```
Constitution.md のステークホルダーテーブルに以下を追加することを推奨します:

| [名前] | [ロール] | [GitHub ハンドル] | [担当領域] |

追加する場合は Constitution.md を直接編集してください。
（Constitution.md の変更は原則決定工程の変更なので、チームリードの確認が必要です）
```

### STEP 7: オンボーディングチェックリスト

```markdown
## ✅ オンボーディングチェックリスト

### 必須（初日中に完了）
- [ ] リポジトリのクローンと開発環境の起動確認
- [ ] Constitution.md を読んだ
- [ ] CLAUDE.md を読んだ（特に「実装開始の必須手順」）
- [ ] 担当領域の仕様書を読んだ
- [ ] /task-start の流れを理解した

### 推奨（1週間以内）
- [ ] /review-patterns で過去のレビュー指摘を確認した
- [ ] 既存のテスト（tests/e2e/）を読んで、テスト記述スタイルを把握した
- [ ] 最初の PR を出した
- [ ] /sdd-health を実行してプロジェクトの健全性を確認した
```

---

## 注意事項

- オンボーディング資料はチャット内で完結させ、別ファイルは作らない（ドキュメントが増えすぎるため）
- Constitution.md の内容はオンボーディング時点の内容を読み込み、変更はしない
- 担当領域が未定の場合は STEP 3〜5 をスキップしてよい
