# /pr-review — PR レビューガイド（SDD 準拠チェック）

**使う場面**: 工程5（実装）。他のメンバーが出した PR をレビューするとき。仕様書・設計書との整合を確認しながらレビューコメントを作成する。

---

## 目的

PR が「仕様書の受入基準を満たしているか」「承認済み設計書に従って実装されているか」を
SDD の観点でチェックし、レビューコメントの雛形を生成する。

---

## 実行手順

### STEP 1: PR の特定

引数で PR 番号が指定された場合はそれを使用する。`/pr-review 42` のように呼び出す。

指定がない場合、以下を確認する:

```bash
gh pr list --state open
```

どの PR をレビューするか選択させる。

### STEP 2: PR の内容取得

```bash
gh pr view [PR番号]
gh pr diff [PR番号]
```

PR の概要・変更ファイル・差分を取得する。

### STEP 3: 関連仕様書・設計書の読み込み

PR タイトル・ブランチ名・変更ファイルから関連する Spec ID を特定する。

```
ブランチ名: feat/[タスク概要] または feat/T-[タスク番号]-[タスク概要]
→ tasks/task-list.md から対応タスクを確認
→ タスクの specId から Spec ID（例: SPEC-AUTH-001）を特定
→ docs/spec/ から仕様書を読み込む
→ docs/design/ から設計書を読み込む
```

### STEP 4: SDD チェックリストの評価

以下の観点を順に評価し、各項目に ✅ / ⚠️ / ❌ を付ける:

#### A. 仕様書整合チェック
| # | 確認項目 | 判定 |
|---|---------|------|
| A-1 | PR が参照する仕様書は `status: approved` か | |
| A-2 | 仕様書に記載された受入基準をすべてカバーしているか | |
| A-3 | 仕様書に書かれていない機能が追加されていないか（スコープ外実装） | |
| A-4 | エラーメッセージ・文言が仕様書の記載と一致しているか | |

#### B. 設計書整合チェック
| # | 確認項目 | 判定 |
|---|---------|------|
| B-1 | 承認済み設計書（`docs/design/[SPEC-ID]-design.md`）が存在するか | |
| B-2 | API エンドポイント・メソッド・レスポンス形式が設計書通りか | |
| B-3 | コンポーネント構成・ファイル配置が設計書の意図と一致するか | |
| B-4 | DB スキーマ・フィールド名が設計書と一致するか | |

#### C. テスト充足チェック
| # | 確認項目 | 判定 |
|---|---------|------|
| C-1 | `tests/e2e/` に当該 Spec ID のテストファイルが存在するか | |
| C-2 | 受入基準の Given/When/Then がテストケースに対応しているか | |
| C-3 | 異常系（エラー・バリデーション）のテストが書かれているか | |
| C-4 | CI（GitHub Actions）が通過しているか | |

#### D. コード品質チェック
| # | 確認項目 | 判定 |
|---|---------|------|
| D-1 | インタラクティブ要素に `data-testid` が付与されているか | |
| D-2 | ハードコードされたシークレット・APIキーがないか | |
| D-3 | Constitution.md のセキュリティ原則に反する実装がないか | |
| D-4 | コミットメッセージのフォーマットが規則に従っているか | |

### STEP 5: レビューコメントの生成

チェック結果をもとに、以下のフォーマットでレビューコメントを生成する:

```markdown
## SDD PR レビュー: #[PR番号] [PR タイトル]

### 総合判定: ✅ Approve / ⚠️ Request Changes / ❌ 要修正

---

### 仕様書整合
[各チェック結果]

### 設計書整合
[各チェック結果]

### テスト充足
[各チェック結果]

### コード品質
[各チェック結果]

---

### 必須修正事項（マージ前に対応が必要）
- [❌ 項目があれば列挙]

### 推奨改善事項（次スプリントでも可）
- [⚠️ 項目があれば列挙]

### 良かった点
- [✅ 特筆すべき点があれば]
```

### STEP 6: GitHub へのコメント投稿（任意）

「GitHub にコメントを投稿しますか？」と確認する。

`yes` の場合:

```bash
gh pr review [PR番号] --comment --body "[生成したコメント]"

# 承認する場合
gh pr review [PR番号] --approve --body "[コメント]"

# 修正要求する場合
gh pr review [PR番号] --request-changes --body "[コメント]"
```

---

## 判定基準

| 判定 | 条件 |
|------|------|
| ✅ Approve | A・B・C・D すべてに ❌ がない |
| ⚠️ Request Changes | ❌ が 1〜2 件（軽微な修正で対応可能） |
| ❌ 要修正 | 仕様書未承認 / 受入基準未達 / テストなし など根本的な問題あり |

---

## 注意事項

- レビューはコードの「良し悪し」ではなく「仕様書通りか」を軸に行う
- 仕様書に書かれていない実装は原則 NG（スコープ外）。必要なら `/spec-change` を案内する
- ❌ があっても人格否定や感情的なコメントにならないよう出力を調整する
