# /bug-triage — バグのトリアージ・修正パス決定

**使う場面**: 開発中にバグが発見されたとき。重篤度の分類・関連仕様の特定・修正パスの決定を行う。
本番障害は `/incident-handle` を使うこと。

---

## 目的

発見されたバグを SDD の観点で分類し、「仕様書の問題か実装の問題か」を切り分けた上で、
適切な修正ブランチと対応フローを決定する。

---

## 実行手順

### STEP 1: バグの内容確認

引数またはフリーテキストでバグの概要を受け取る。

情報が不足している場合、以下を質問する:

```
1. どの機能で発生しているか（画面名・API・操作）
2. 期待する動作は何か
3. 実際の動作は何か
4. 再現手順（任意）
5. 発見した環境（dev / staging / prod）
```

### STEP 2: 重篤度の判定

以下の基準で重篤度を判定する:

| 重篤度 | 基準 | 対応速度 |
|--------|------|---------|
| 🔴 Critical | データ破壊 / セキュリティ脆弱性 / 全ユーザー影響 | 即日対応 → `/incident-handle` へ誘導 |
| 🟠 High | 主要機能が使えない / 一部ユーザーの業務停止 | 当スプリント内で修正 |
| 🟡 Medium | 機能は動くが挙動が仕様と異なる | 次スプリントに計画 |
| 🟢 Low | UI の軽微な不整合 / パフォーマンスの軽微な問題 | バックログに積む |

🔴 Critical の場合、`/incident-handle` の実行を強く推奨して中断する。

### STEP 3: 関連仕様書の特定

バグが発生している機能の仕様書を `docs/spec/` から検索する:

```bash
grep -r "[バグに関連するキーワード]" docs/spec/
```

該当仕様書を読み込み、以下を判断する:

| 判断 | 意味 | 次のアクション |
|------|------|--------------|
| **実装バグ** | 仕様書は正しく、コードが仕様通りに動いていない | 修正ブランチを作成して実装を直す |
| **仕様書バグ** | 仕様書の受入基準が不明確・矛盾・誤りがある | `/spec-change` で仕様書を先に修正する |
| **仕様書に記載なし** | 想定されていないケースでバグが起きている | `/spec-write` で仕様を追加してから修正する |

### STEP 4: 修正パスの決定と案内

分類・重篤度に応じて対応フローを案内する:

#### パターン A — 実装バグ（High/Medium）

```
✅ 修正パス: 通常の fix ブランチフロー

1. git checkout -b fix/[バグ概要]
2. バグを修正する
3. /test-write → 再現テスト + 修正テストを追加
4. /test-run   → テストが通ることを確認
5. /task-done  → PR を作成（レビュー依頼）
6. /pr-review  → レビュアーはこのスキルでチェック
```

#### パターン B — 実装バグ（Low）

```
✅ 修正パス: バックログに積む

次のスプリント計画（/tasks-plan）でタスクとして取り込んでください。
```

#### パターン C — 仕様書バグ

```
⚠️ 修正パス: 仕様書先行修正フロー

仕様書に問題があるため、仕様書を先に修正します:

1. /spec-change [SPEC-ID]  → 仕様書の変更フローを開始
2. 仕様書が approved に戻ったら
3. git checkout -b fix/[バグ概要]
4. 修正実装 → /test-write → /test-run → /task-done
```

#### パターン D — 仕様書に記載なし

```
⚠️ 修正パス: 仕様書追加フロー

このケースは仕様書に定義がないため、仕様を先に確定させます:

1. /spec-write  → 不足仕様を追加
2. /spec-review → 仕様書をレビュー・承認
3. /design-create → 必要に応じて設計書を更新
4. /task-start  → 実装開始
```

### STEP 6: サマリー表示

```
🐛 バグトリアージ完了

  重篤度:   [Critical / High / Medium / Low]
  分類:     [実装バグ / 仕様書バグ / 仕様書未定義]
  関連仕様: [Spec ID]
  修正パス: [A / B / C / D]

次のアクション:
  [パターンに応じた次のスキル]
```

---

## 注意事項

- 「バグっぽい」と感じても、仕様書を確認してから修正に入る。仕様通りの場合もある
- 修正実装であっても、設計書の存在チェック（`/task-start` のゲート）は省略しない
- 本番環境で発生している場合は重篤度を一段階上に評価する
