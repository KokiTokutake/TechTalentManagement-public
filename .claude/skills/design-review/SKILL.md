# /design-review — 多エージェント設計レビュー（自動改善ループ）

**使う場面**: 工程3（設計計画）。設計書を作成・更新した後、実装に進む前。
6つの専門エージェントが並列レビューし、スコアが閾値（デフォルト80点）を超えるまで
設計書を自動改善するループを実行する。

---

## アーキテクチャ概要

```
/design-review オーケストレーター
│
├── STEP 1: ファイル読み込み・設定確認
│
├── STEP 2: 第1ラウンド（6エージェント 並列起動）
│   ├── Agent A: アーキテクチャ専門家  ── 20点
│   ├── Agent B: セキュリティ専門家    ── 20点
│   ├── Agent C: データモデル専門家    ── 15点
│   ├── Agent D: API 設計専門家        ── 15点
│   ├── Agent E: テスト容易性専門家    ── 15点
│   └── Agent F: 要件充足専門家        ── 15点
│                                  合計 100点
│
├── STEP 3: スコア集計
│   ├── ≥ 閾値（80点） ──→ STEP 5（承認フロー）
│   └── < 閾値         ──→ STEP 4（改善ループ）
│
├── STEP 4: 改善ループ（最大 3 回）
│   ├── 最低スコア順に問題を優先抽出
│   ├── 設計書を自動編集（Edit ツール）
│   ├── 低スコアのエージェントのみ再実行
│   ├── スコア更新 → 閾値チェック
│   └── ループ終了条件: ≥80点 or 3回完了
│
└── STEP 5: 最終レポート + 承認フロー
```

---

## STEP 1: 準備

### 1-1. 設定の確認

```
レビュー設定を確認します:

- 合格閾値: 80点（変更しますか？）
- 最大ループ回数: 3回（変更しますか？）
- 対象設計書:
  1. docs/design/architecture.md のみ
  2. docs/design/component-design.md のみ
  3. 両方（デフォルト）
```

### 1-2. ファイル読み込み

以下を全て読み込む:
- `docs/design/architecture.md`
- `docs/design/component-design.md`
- `docs/spec/` 配下の全 approved 仕様書
- `.constitution/Constitution.md`
- `playwright.config.ts`（存在する場合）

ファイルが存在しない場合は「存在しないため N/A」として扱い、該当エージェントのスコア算定から除外する。

## STEP 2: 第1ラウンド — 全エージェント並列起動

以下の 6 エージェントを **同時に** 起動する（`Agent` ツールを 1 メッセージで複数呼び出し）。
各エージェントには下記の「エージェント定義」セクションのプロンプトを渡す。

## エージェント定義

### Agent A: アーキテクチャ専門家（満点 20点）

**専門領域**: システム構成・設計パターン・スケーラビリティ・保守性

**スコアリング基準**:
```
[4点] レイヤー分離
  - プレゼンテーション/ビジネスロジック/データアクセスが明確に分離されているか
  - 各レイヤーの責務が定義されているか

[4点] 依存関係の方向
  - 依存関係が適切な方向を向いているか（循環依存がないか）
  - 依存性逆転の原則（DIP）が考慮されているか

[4点] スケーラビリティ
  - 想定負荷に対してアーキテクチャが成立するか
  - ボトルネックが特定・対処されているか

[4点] 技術選定の根拠
  - 採用技術の選定理由が記録されているか
  - 不採用技術の理由が記録されているか

[4点] 変更容易性
  - 将来の変更に対して影響範囲が局所化されているか
```

## STEP 4: 改善ループ（最大 3 回）

### ループ構造

```
iteration = 1
while 合計スコア < 80点 AND iteration ≤ 3:

  1. 最低スコアエージェントの特定
     → 達成率が最も低いエージェントを 1〜3 つ選択
     → 「重大な問題」がある場合は優先

  2. 優先改善点の抽出
     → 選択したエージェントの「改善提案」を優先度順に列挙
     → 「修正後の期待スコア」が高い改善を優先

  3. 改善内容の確認（Human-in-the-Loop）
     「以下の改善を設計書に適用します。確認してください:
      [改善内容の一覧]
      → 適用: yes / 内容を変更: no / スキップ: skip」

  4. 設計書の自動編集
     → Edit ツールで docs/design/*.md を修正
     → 変更内容をユーザーに提示

  5. 低スコアエージェントの再実行（並列）
     → 改善が行われたエージェントのみを再起動
     → 全エージェントの再実行は行わない（効率化）

  6. スコア更新
     → 再実行エージェントの新スコアで集計表を更新
     → 改善幅を表示（例: Agent B: 12→17点 +5点）

  iteration += 1
```

### ループ終了条件

| 条件 | 処理 |
|------|------|
| 合計 ≥ 80点 | ✅ ループ終了 → STEP 5 |
| 3回完了・まだ80点未満 | ⚠️ ループ終了 → ユーザーに判断を委ねる |
| ユーザーが「停止」と入力 | 現状でレポートを生成 |

### 3回終了後も基準未達の場合

```
⚠️ 3回の改善ループを完了しましたが、合計スコアが X点（目標80点）に留まっています。

選択してください:
A) このまま進める（実装リスクを承知の上で）
B) 設計書を手動で修正してから再度 /design-review を実行する
C) /design-create からやり直す
D) 閾値を下げて承認する（現状の X点で承認）
```

```
  /tasks-plan → タスク分割に進む
```

### 条件付き合格（閾値調整・ループ上限）の場合

```
⚠️ 条件付き合格（XX/100点）

以下のリスクを承知の上で実装を進めることができます:
[残存課題一覧]

テックリードの承認を取得してから /tasks-plan に進んでください。
```

---

## 設定オプション

| オプション | デフォルト | 説明 |
|-----------|-----------|------|
| 合格閾値 | 80点 | 例: 「閾値を70点に変更」と指定可能 |
| 最大ループ回数 | 3回 | 例: 「ループを5回まで」と指定可能 |
| 実行エージェント | 全6種 | 例: 「AgentBとFだけ実行」と指定可能 |
| 自動改善モード | 確認あり | 「自動で適用（確認なし）」と指定可能 |
