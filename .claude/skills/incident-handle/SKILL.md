# /incident-handle — インシデント対応ガイド

**使う場面**: 工程7（運用）。本番環境で問題が発生したとき。障害の分類・初動対応・エスカレーションをガイドする。

---

## 目的

`docs/guides/operation-runbook.md` のインシデント対応フローに従い、
障害レベルの分類・初動対応・原因分析・報告書作成を素早く実施できるようにガイドする。

---

## 実行手順

### STEP 1: 症状の確認

```
緊急度を判断するために教えてください:

1. どんな症状が起きていますか？
   （例: ページが表示されない / ログインできない / 処理が遅い）

2. 影響範囲はどのくらいですか？
   a) 全ユーザーが使えない
   b) 一部の機能が使えない
   c) 特定のユーザーだけ影響
   d) パフォーマンスが低下している

3. いつから発生しましたか？

4. 直前にデプロイや設定変更はありましたか？
```

### STEP 2: インシデントレベルの判定

`docs/guides/operation-runbook.md` のアラートレベル定義に基づいて判定し、表示する:

```
📊 インシデントレベル判定: P1（Critical）

理由: 全ユーザーがサービスを利用できない状態です

P1 の初動:
  ⏱️ 初動時間: 15分以内
  👥 対応者: オンコール全員を召集
  📢 通知先: テックリード・マネージャー・経営層

今すぐ以下を実施してください:
1. 関係者への一次連絡（Slack / 電話）
2. ステータスページの更新（"調査中" に設定）
3. ロールバックを検討
```

### STEP 3: 状況確認の案内

```
以下を確認してください（確認したら教えてください）:

[ ] アプリケーションログの確認
    → 監視ダッシュボードのエラーログを確認
    → 直前のエラーメッセージは？

[ ] インフラ状態の確認
    → CPU / メモリ / ディスク使用率は正常か？
    → DB 接続数は正常か？

[ ] 直前デプロイの確認
    → 直近のデプロイは何時か？
    → ロールバックで回復できそうか？
```

ユーザーの確認結果をもとに次の対応を案内する。

### STEP 4: 対応方針の確認

```
原因の仮説はありますか？

考えられる原因:
1. 直前デプロイのバグ → ロールバックを実施
2. インフラ障害 → クラウドプロバイダーのステータス確認
3. DB の問題 → コネクション数・スロークエリを確認
4. 外部 API の障害 → 外部サービスのステータス確認

どれに当てはまりそうですか？
```

### STEP 5: ロールバック手順（必要な場合）

```
ロールバックを実施しますか？

GitHub Actions の "Rollback" ワークフローを実行:
  gh workflow run rollback.yml -f version=v1.1.9

または Git タグからロールバック:
  git tag --list 'v*' | sort -V | tail -5
```

### STEP 6: 復旧確認

```
復旧を確認してください:
[ ] ヘルスチェックエンドポイントが 200 を返している
[ ] 主要機能が正常に動作している
[ ] エラー率が正常レベルに戻っている
[ ] ユーザーへの影響が解消されている
```

### STEP 7: インシデントレポートの作成

復旧後:

```markdown
## インシデントレポート

発生日時: YYYY-MM-DD HH:MM
復旧日時: YYYY-MM-DD HH:MM
影響時間: X 分
インシデントレベル: P1 / P2 / P3 / P4
影響範囲: [ユーザー数/機能]

### 原因
[根本原因]

### 対応内容
1. [実施した対応]

### 再発防止策
1. [対策]

### アクションアイテム
| 対策 | 担当 | 期限 |
|------|------|------|
| [対策] | @handle | YYYY-MM-DD |
```

「インシデントレポートを保存しますか？」と確認する。
